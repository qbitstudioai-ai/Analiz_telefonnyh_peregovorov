# Словарь данных Supabase

Статус: DOC-12. Документ задаёт логическую модель данных будущего Supabase/PostgreSQL: какие сущности нужны, что они означают, как связаны, откуда берётся факт и кто имеет право его создавать или изменять.

Это не SQL, не миграция, не окончательные названия таблиц/колонок и не выбор типов PostgreSQL. Рабочие коды нужны для однозначного обсуждения и последующего проектирования.

## Цель

После DOC-12 должно быть возможно по одному звонку восстановить цепочку:

событие источника  
→ логический звонок  
→ операции и попытки  
→ временное аудио  
→ исходная транскрипция и technical speaker  
→ назначение ролей  
→ псевдонимизированная версия и privacy-пакет  
→ использованные знания/методика/промт  
→ анализ и доказательства  
→ подтверждённые CRM-факты  
→ исходящее действие и попытки доставки  
→ данные дашборда.

При этом исходный факт, вывод ИИ, подтверждение CRM и производная метрика не должны становиться одной неразличимой записью.

## Общие правила данных

### Контур

Каждая бизнес-сущность находится внутри одного контура «компания + среда» по DOC-10.

Физически контур уже задаётся отдельной schema и runtime-Credential. Поэтому DOC-12 не требует обязательно дублировать company/environment в каждой строке отдельными колонками. Но принадлежность записи контуру должна быть однозначна и проверяема.

Поле из входного payload не может переключить контур.

### Внутренний ID

Каждая самостоятельная сущность имеет внутренний стабильный ID.

Внешний ID источника не заменяет внутренний ID и всегда хранится вместе с областью его действия: адаптер + конкретное подключение/аккаунт.

### Происхождение

Для факта, пришедшего извне или созданного системой, должно быть возможно установить происхождение:

- источник/адаптер;
- внешний ID, если есть;
- операция, которая создала результат;
- время источника и/или время получения;
- версия правил/входов, когда факт вычисляемый.

### История вместо бесследного перезаписывания

Версионируемые или исправляемые данные не должны терять предыдущий подтверждённый вариант.

Ручное исправление создаёт отдельное событие исправления и, если нужно, новую версию зависимых сущностей.

### Текущая версия и история

Если сущность может иметь несколько версий, система должна уметь определить:

- все версии;
- какая версия была использована конкретной зависимой операцией;
- какая версия считается текущей действующей для пользовательского представления;
- почему прежняя версия перестала быть текущей.

Точные правила версионирования определит DOC-13.

### Время

Нужно различать:

- время события у источника;
- время приёма системой;
- время начала/окончания операции;
- время подтверждённого бизнес-факта;
- время создания/изменения записи.

Дашбордовый период для звонков определяется по времени начала логического звонка по [METRICS](specs/METRICS.md).

### Секреты

Пароли, API tokens, service_role, PostgreSQL credentials и другие секреты не являются бизнес-данными этого словаря и не хранятся в обычных таблицах Supabase.

Допустима только безопасная ссылка/код используемого подключения, не раскрывающая секрет.

## Канонические поля операций

DOC-11 уже закрепил логический смысл следующих полей, который DOC-12 должен сохранить в хранении:

- contract_version;
- scope_ref;
- call_ref;
- operation_id;
- attempt_id;
- operation_type;
- correlation_id;
- input_refs;
- decision;
- operation_state;
- result_ref;
- external_request_ref;
- error_class;
- error_code;
- requested_at;
- completed_at.

Физически часть этих значений может находиться в разных сущностях, но их смысл не должен теряться.

## 1. События звонков — sobytia_zvonkov

Одна запись соответствует одному полученному событию/сигналу источника.

Ключевые данные по смыслу:

- внутренний event ID;
- код адаптера;
- ссылка на конкретное серверно настроенное подключение;
- внешний event ID, если источник его предоставляет;
- внешний call ID, если источник его предоставляет;
- тип/стадия события;
- время события у источника;
- время приёма;
- направление/статус ответа, если источник подтверждает;
- доверенные ссылки participant/extension/CRM, если доступны;
- признак готовности аудио;
- decision accepted/duplicate/rejected;
- ссылка на call_ref после разрешения звонка;
- безопасный код отклонения/дубля.

Создаёт: входной адаптер/n8n.

Источник истины для внешнего факта: конкретный источник звонка.

Изменение: исходное полученное событие не переписывается как будто пришло другим. Поздние сведения приходят новым событием.

## 2. Логические звонки — zvonki

Одна запись соответствует одному логическому звонку, а не одному webhook.

Ключевые данные:

- внутренний call_ref;
- область внешней идентичности источника;
- внешний стабильный call ID, если он есть;
- менеджер;
- доверенные локальные ссылки на контакт/сделку/обращение без раскрытия их внешней модели в CORE;
- время начала/окончания и длительность;
- направление;
- подтверждённый статус ответа;
- первый/повторный;
- клиентский/исключённый/пропущенный;
- текущее состояние обработки;
- ссылка на текущее решение фильтра;
- ссылка на текущий действующий анализ, если он есть.

Создаёт: n8n/CORE после регистрации и защиты от дублей.

Не создаёт: LLM.

Один звонок может иметь много событий, операций, транскрипций и анализов, но остаётся одним звонком.

## 3. Менеджеры — menedzhery

Содержит доверенную сущность сотрудника, нужную для связей звонков и дашборда.

Ключевые данные:

- внутренний manager ID;
- внешний ID сотрудника в доверенном источнике;
- источник/область этого внешнего ID;
- ФИО в локальном защищённом контуре;
- отдел/команда, если подтверждены;
- активность/период действия привязки;
- история изменившихся внешних привязок.

Создаёт/обновляет: n8n из доверенного источника или разрешённая административная операция.

LLM не назначает manager ID.

## 4. Связи звонков — svyazi_zvonkov

Нужны для повторных разговоров и истории клиента/сделки.

Ключевые данные:

- текущий call_ref;
- предыдущий call_ref или доверенная сущность обращения/сделки;
- вид связи;
- подтверждённость;
- доверенный идентификатор/основание;
- источник определения;
- время создания;
- ручное подтверждение/исправление, если было.

Совпадение имени или догадка LLM не является подтверждённой связью.

## 5. Решения фильтра — resheniya_filtra

Каждое окончательное или версионируемое решение фильтра хранит:

- call_ref;
- принято/исключено/пропущено;
- стабильный код причины;
- версию правил фильтра;
- входные факты/основание;
- операцию, которая приняла решение;
- время.

Фильтр не уничтожает зарегистрированный звонок.

## 6. Логические операции — operacii

Одна запись = одна идемпотентная логическая операция, например получить аудио, транскрибировать, анализировать или отправить обратную связь.

Обязательный смысл:

- operation_id;
- call_ref;
- operation_type;
- contract_version;
- input_refs;
- текущее operation_state;
- result_ref;
- время запроса и завершения;
- итоговый error_class/error_code, если операция не успешна;
- ссылка на предыдущую/заменяемую операцию при новом версионированном результате, если это потребуется DOC-13.

operation_id не меняется при безопасном retry той же логической операции.

## 7. Попытки операций — popytki_operaciy

Одна логическая операция может иметь много попыток.

Хранится:

- attempt_id;
- operation_id;
- номер/порядок попытки по смыслу;
- время начала/окончания;
- состояние попытки;
- внешний request ID, если есть;
- transport result;
- decision;
- error_class/error_code;
- безопасный технический контекст;
- причина повтора/ручного запуска.

Техническая ошибка является свойством/результатом попытки. Отдельная копия истины «ошибка обработки» не должна расходиться с попыткой.

Для дашборда/мониторинга допускается производное представление ошибок.

## 8. Временные аудиоартефакты — vremennye_audio_artefakty

Supabase хранит только метаданные временного локального аудио, а не постоянный аудиофайл.

Нужно хранить:

- call_ref;
- operation_id получения;
- разрешённую локальную ссылку/идентичность артефакта;
- состояние получения/готовности;
- размер/длительность/признаки целостности, если используются проверкой;
- время создания;
- deadline/условие удаления по политике внедрения;
- время фактического удаления;
- подтверждение удаления;
- состояние cleanup/ошибки;
- происхождение аудио.

Сам бинарный звук не становится постоянной записью Supabase.

## 9. Исходные транскрипции — ishodnye_transkripcii

Отдельная защищённая сущность по DOC-09.

Хранит:

- transcript ID и версию;
- call_ref;
- ссылку на аудиоверсию/операцию;
- фактический движок/модель/конфигурацию;
- исходный текст или защищённое представление;
- состояние проверки;
- время создания;
- политику/условие хранения;
- связь с последующими версиями при исправлении.

Доступ ограничен. Внешняя LLM исходную транскрипцию не получает.

## 10. Сегменты транскрипции — segmenty_transkripcii

Сегмент принадлежит конкретной версии исходной транскрипции.

Хранит:

- transcript ID;
- стабильный внутри версии segment ID;
- порядок;
- начало/конец;
- technical speaker;
- текст исходного сегмента;
- доступные технические показатели качества.

Бизнес-роль МЕНЕДЖЕР/КЛИЕНТ не должна безусловно подменять technical speaker в этой сущности.

## 11. Назначения ролей — naznacheniya_rolej

Отделяют технического speaker от бизнес-роли.

Хранит:

- версию назначения ролей;
- transcript ID;
- technical speaker;
- назначенную роль;
- статус: подтверждена / предположена / не определена;
- доверенное основание;
- конфликт источников, если есть;
- связь с конкретным менеджером, когда подтверждено;
- автора/основание ручного исправления;
- время.

Изменение ролей не стирает прежнее назначение бесследно и может потребовать новую версию downstream-анализа.

## 12. Псевдонимизированные транскрипции — psevdonimizirovannye_transkripcii

Это отдельная версия/сущность от исходной транскрипции.

Хранит:

- ID/версию;
- call_ref;
- ссылку на исходную транскрипцию;
- ссылку на версию назначения ролей;
- псевдонимизированный текст/сегменты, разрешённые продукту;
- происхождение;
- время создания;
- состояние privacy-проверки;
- политику хранения.

Она не содержит таблицу обратного соответствия.

## 13. Privacy-пакеты — privacy_pakety

Фиксируют конкретный подготовленный контекст, на котором разрешён внешний LLM-вызов.

Хранит:

- package ID/версию;
- call_ref;
- ссылку на псевдонимизированную транскрипцию;
- ссылку на роли;
- ссылку на разрешённый контекст истории;
- privacy status passed/blocked;
- безопасные коды найденных проблем;
- время проверки;
- операцию подготовки;
- ссылку на LLM operation, если вызов был разрешён.

Полное содержимое может храниться как разрешённый версионированный пакет либо воспроизводиться из ссылок — точный способ выбирается при реализации. Но должно быть доказуемо, какой пакет реально ушёл наружу.

## 14. Соответствия псевдонимов — sootvetstviya_psevdonimov

Самая защищённая часть privacy-данных.

Хранит только то, что необходимо для разрешённого обратного сопоставления:

- область псевдонима;
- псевдоним;
- защищённую локальную ссылку/реальное значение;
- цель/основание;
- время создания;
- срок/условие хранения.

Не доступно внешней LLM, embedding API, обычному браузеру и стандартным логам.

Псевдоним не создаёт глобальный ID человека между компаниями.

## 15. Качество обработки — kachestvo_obrabotki

Отдельно от анализа качества менеджера.

Хранит по версии обработки:

- call_ref;
- ссылку на аудио/транскрипцию/роли;
- качество аудио;
- показатели транскрипции;
- надёжность ролей;
- итог nadezhno/predvaritelno для использования анализа;
- причины предупреждения;
- версию правил качества.

Качество обработки не является баллом менеджера.

## 16. Метрики речи — metriky_rechi

Хранит вычисленные параметры речи, когда качество позволяет:

- call_ref/analysis or transcript ref;
- доля речи менеджера/клиента;
- паузы;
- перебивания;
- скорость речи;
- длительность разговора;
- версия правил/порогов;
- надёжность расчёта.

Метрики речи не изменяют общий балл автоматически.

## 17. Публикации знаний — publikacii_znanij

Логическая версия набора знаний, разрешённая продуктам компании.

Минимально:

- publication ID/version;
- состояние draft/published/archived по смыслу;
- время публикации;
- автор/происхождение изменения;
- состав разрешённых документов/версий.

Обычный анализ читает только published.

Точный workflow публикации завершит DOC-17.

## 18. Документы знаний — dokumenty_znanij

Хранит:

- внутренний document ID;
- безопасное название/метаданные;
- источник документа;
- версию содержимого;
- состояние;
- время создания/обновления;
- связь с публикациями;
- разрешения на внешний embedding, если политика внедрения это требует.

Реальные закрытые документы клиента не публикуются в GitHub.

## 19. Фрагменты знаний — fragmenty_znanij

Chunk конкретной версии документа.

Хранит:

- fragment ID;
- document/version ref;
- текст разрешённого фрагмента;
- порядок/позицию;
- данные для ссылки в доказательстве;
- состояние публикации через publication;
- версию chunking/подготовки, когда она станет частью воспроизводимости.

## 20. Embeddings знаний — embeddingi_znanij

Хранит:

- fragment ID;
- vector representation;
- модель/провайдер/version;
- параметры подготовки, которые влияют на воспроизводимость;
- время расчёта;
- операцию расчёта;
- статус.

Embedding не является источником текста документа и не заменяет fragment.

## 21. Версии промта — versii_promta

Нужно уметь сохранить неизменяемую версию промта, реально использованную анализом.

Минимально:

- prompt version ID;
- содержимое/разрешённая ссылка;
- статус;
- время активации;
- автор/источник изменения.

Точные правила supersede/current определит DOC-13.

## 22. Версии методики — versii_metodiki

Содержит версию:

- набора критериев;
- применимости;
- весов;
- шкалы;
- обязательных этапов;
- правил интерпретации результата;
- иных параметров, реально влияющих на оценку.

Оценка критерия всегда ссылается на версию методики.

## 23. Версии правил фильтра — versii_pravil_filtra

Хранит неизменяемую версию правил, которой принято решение фильтра.

Должно быть возможно объяснить, почему звонок был исключён в момент обработки, даже если настройки позже изменились.

## 24. Анализы — analizy

Одна запись = одна версия проверенного CORE анализа конкретного звонка.

Хранит:

- analysis ID/version;
- call_ref;
- operation_id анализа;
- privacy package ref;
- transcript/role refs;
- prompt version;
- methodology version;
- model/provider version;
- knowledge publication/version;
- контекст истории version/ref при использовании;
- общий балл;
- статус завершения;
- надёжность nadezhno/predvaritelno;
- время анализа;
- признак текущей действующей версии по правилам DOC-13;
- связь с заменяемой/предыдущей версией.

Ответ LLM до проверки CORE не становится analizy.

## 25. Оценки критериев — ocenki_kriteriev

Хранит:

- analysis ID;
- stable criterion code;
- применимость;
- балл 1–10, если применим;
- вес из использованной методики;
- комментарий/обоснование;
- ссылки на доказательства.

«Не применимо» не хранится как ноль.

## 26. Этапы звонка — etapy_zvonka

Хранит на конкретный анализ:

- stable stage code;
- применимость;
- достигнут/пропущен;
- порядок;
- обязательность в этой методике;
- ссылки на доказательства.

Прохождение этапа и качество выполнения критерия остаются разными фактами.

## 27. Наблюдения анализа — nablyudeniya_analiza

Хранит:

- analysis ID;
- stable observation code;
- тип: ошибка / сильная сторона / предупреждение;
- применимость;
- серьёзность по методике, если используется;
- пояснение;
- criterion/stage ref;
- ссылки на доказательства.

Стабильный код позволяет агрегировать повторяющиеся ошибки.

## 28. Доказательства — dokazatelstva

DOC-12 фиксирует только сущность и связи; полный смысл завершит DOC-14.

Минимально доказательство связывает:

- конкретный вывод/оценку/наблюдение;
- segment ID или разрешённую цитату;
- таймкод;
- правило/критерий;
- knowledge fragment/document/version, если вывод основан на знаниях;
- analysis version.

LLM не может сослаться на segment/chunk, отсутствующий во входном пакете, и превратить ссылку в подтверждённое доказательство.

## 29. Предполагаемые результаты ИИ — rezultaty_ii

Отдельно от CRM-фактов.

Хранит:

- analysis ID;
- тип результата;
- целевое действие;
- уверенность, если методика её использует;
- следующий ожидаемый контакт/срок как вывод разговора;
- ссылки на доказательства;
- статус результата.

Не является подтверждением продажи.

## 30. Подтверждения CRM/человека — podtverzhdeniya_crm

Одна запись = отдельный доверенно подтверждённый бизнес-факт.

Хранит:

- call/client/deal ref;
- тип: замер/встреча/счёт/договор/оплата/другой согласованный факт;
- внешний ID факта, если есть;
- источник;
- значение/статус;
- время факта;
- время получения системой;
- автора ручного подтверждения, если источник человек;
- историю исправления/отмены.

ИИ-результат и CRM-факт не перезаписывают друг друга.

## 31. Связи пропуска и перезвона — svyazi_perezvonov

Хранит:

- missed call_ref;
- callback call_ref;
- manager;
- доверенное основание связи;
- подтверждённость;
- время между звонками;
- версию/параметры окна компании;
- источник решения.

Неоднозначная связь не считается подтверждённым перезвоном.

## 32. Исходящие действия — iskhodyashchie_deystviya

Создаются до внешней отправки.

Хранит:

- outgoing action ID;
- call_ref;
- analysis version;
- назначение/тип обратной связи;
- server-selected channel ref;
- trusted recipient ref;
- message content/version;
- operation_id отправки;
- состояние действия;
- время создания.

Одинаковая версия анализа + то же назначение не создают второе равнозначное действие из-за дубля webhook.

## 33. Попытки доставки — popytki_dostavki

Отдельны от исходящего действия.

Хранит:

- delivery attempt ID;
- outgoing action ID;
- attempt_id / operation_id;
- provider request/message ID;
- время попытки;
- transport result;
- provider-confirmed status;
- подтверждённое время доставки, если доступно;
- error_class/error_code;
- возможность безопасного retry;
- итог succeeded / failed_retryable / failed_requires_fix / outcome_unknown.

«Принято API» и «доставлено» различаются согласно фактической семантике канала.

## 34. Ручные исправления — ispravleniya

Аудит разрешённых ручных изменений.

Хранит:

- correction ID;
- тип и ID целевой сущности;
- исправляемое значение/аспект;
- прежнее значение или безопасную ссылку на прежнюю версию;
- новое значение/новую версию;
- автор;
- время;
- причина;
- статус проверки/применения;
- downstream-сущности, требующие перерасчёта, если применимо.

Исправление не удаляет историю исходного машинного результата.

## Что не является отдельным первичным источником истины

### Технические ошибки

Ошибка операции хранится на popytki_operaciy через error_class/error_code и состояние.

Допускается dashboard/view «ошибки обработки», но он не должен стать второй независимой mutable-копией ошибки.

### Обратная связь как единая строка

Пользовательски «обратная связь» может выглядеть как один объект, но данные разделены на:

- iskhodyashchie_deystviya — что намеревались отправить;
- popytki_dostavki — что реально происходило при отправке.

### Метрики дашборда

Карточки «средний балл», «конверсия», «частота ошибки» и подобные значения обычно вычисляются из первичных фактов по [METRICS](specs/METRICS.md).

Они не должны становиться отдельными несогласованными фактами, если могут быть воспроизведены.

Допустимы materialized/cache представления при реализации, но их источник и версия расчёта остаются проверяемыми.

## Удаление и retention

Словарь не задаёт численные сроки.

Особые правила:

- бинарное аудио не хранится постоянно;
- временный аудиоартефакт хранит metadata и подтверждение удаления;
- исходная транскрипция имеет собственную политику;
- псевдонимизированная транскрипция имеет отдельную политику;
- таблица соответствий имеет отдельную наиболее строгую политику;
- удаление должно учитывать backup по DOC-09/DOC-18;
- версия анализа/доказательств может пережить удаление исходного текста только если это разрешено политикой и остаётся достаточная безопасная воспроизводимость.

## Обязательные инварианты

Будущая модель SQL должна обеспечить по смыслу:

1. Событие не существует вне одного контура.
2. Один event не создаёт второй логический звонок из-за повторной доставки.
3. Одинаковый внешний call ID в разных подключениях/компаниях не смешивается.
4. operation_id идентифицирует одну логическую операцию; retry создаёт новый attempt_id.
5. Подтверждённый succeeded одной операции не дублируется повтором.
6. Временное аудио имеет состояние удаления и не превращается в постоянный архив.
7. Исходная и псевдонимизированная транскрипции различимы.
8. Таблица соответствий не читается обычным dashboard/LLM.
9. Technical speaker и бизнес-роль различимы.
10. Анализ ссылается на конкретные версии транскрипции, ролей, privacy-пакета, промта, методики, модели и знаний.
11. Старый анализ не стирается новой версией.
12. «Не применимо» критерия не хранится как ноль.
13. Доказательство связано с конкретным анализом и реальным segment/chunk ref.
14. ИИ-результат и CRM-факт не объединяются.
15. Исходящее действие существует до первой попытки доставки.
16. Доставка имеет историю попыток; unknown не превращается в delivered.
17. Ручное исправление имеет автора, время и причину.
18. Данные разных контуров не связываются внешними ключами/логическими ссылками обычного runtime.
19. Dashboard aggregate воспроизводим из первичных фактов.
20. Секреты не являются значениями бизнес-сущностей.

## Проверяемые сценарии DOC-12

Будущая реализация должна показать как минимум:

1. Два одинаковых webhook создают два факта приёма/попытки при необходимости аудита, но один логический звонок.
2. Поздний callback дополняет существующий call_ref и остаётся отдельным событием.
3. Один звонок имеет несколько attempt одной operation без дублирования результата.
4. После транскрибации можно восстановить используемую аудиоверсию и движок.
5. Из segment видно technical speaker, а роль берётся из отдельного назначения ролей.
6. Из privacy package видно, какая псевдонимизированная версия была проверена и могла уйти LLM.
7. Из analysis однозначно восстанавливаются prompt/methodology/model/knowledge refs.
8. Доказательство не может ссылаться на segment/chunk чужого анализа/контура.
9. Предварительный анализ виден, но отделён от надёжного.
10. Новый анализ не удаляет старый.
11. CRM payment не превращает прежний AI result в тот же объект.
12. Пропущенный и callback являются двумя звонками, связанными отдельной сущностью.
13. Одно outgoing action имеет несколько delivery attempts, если retry разрешён.
14. confirmed delivery запрещает второй эквивалентный внешний эффект.
15. outcome_unknown остаётся видимым состоянием попытки.
16. dashboard error list воспроизводится из operation attempts.
17. Удаление временного аудио оставляет подтверждение удаления без самого файла.
18. Удаление исходной транскрипции по политике не удаляет автоматически разрешённые производные данные без отдельного основания.
19. User A не получает сущности schema B.
20. В обычной бизнес-таблице не находится password/token/service credential.
21. Одинаковая метрика в карточке и выгрузке строится из одного набора первичных сущностей.
22. Ручное исправление позволяет восстановить исходный и новый варианты и автора изменения.

## Что сознательно не определяется DOC-12

- SQL table/column names;
- PostgreSQL types;
- indexes;
- foreign keys в синтаксисе SQL;
- partitioning;
- UUID vs другой физический тип ID;
- RLS/grants;
- точные JSON структуры;
- физическое разделение некоторых версий по отдельным таблицам;
- финальная система current/superseded;
- полный workflow публикации знаний;
- точная модель доказательств.

DOC-13 определит версионирование, DOC-14 — доказательства, DOC-17 — публикацию общей базы знаний, DOC-18 — backup/release/эксплуатацию.

## Критерий DOC-12

Документ готов, если:

- все данные из жизненного цикла, контрактов и дашборда имеют логическое место хранения;
- первичный факт не смешан с выводом ИИ и производной метрикой;
- operation и attempt разделены;
- исходная/псевдонимизированная транскрипция и таблица соответствий разделены;
- знание, его fragment и embedding различимы;
- анализ хранит необходимые ссылки на версии;
- CRM-факты независимы от AI result;
- исходящее действие отделено от попыток доставки;
- для каждой сущности понятны источник и создатель;
- связи позволяют воспроизвести дашборд и расследовать сбой;
- при этом SQL и физическая схема ещё не объявлены реализованными.

SQL, Supabase, n8n, сервер и production в DOC-12 не изменялись.
