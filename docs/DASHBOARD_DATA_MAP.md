# Карта данных дашборда руководителя

Статус: согласованная логическая модель v1.0. Документ определяет, какие данные необходимы интерфейсу, откуда они появляются и как связаны. Это не SQL, не названия готовых таблиц и не подтверждение реализации.

## Главное правило движения данных

~~~mermaid
flowchart LR
    A["CRM / телефония / оператор"] --> B["n8n и CORE"]
    B --> C["Supabase компании"]
    C --> D["Сервер дашборда"]
    D --> E["Браузер руководителя"]
~~~

Правильное толкование фразы «данные приходят из n8n»:

- n8n получает события источников, вызывает обработку и записывает факты и результаты в Supabase;
- Supabase является постоянным источником истины для дашборда;
- сервер дашборда читает разрешённые данные и согласованные представления Supabase;
- браузер не подключается напрямую к PostgreSQL и не получает Credentials n8n;
- дашборд не читает память текущего запуска n8n и не рассчитывает альтернативные показатели из временных execution data.

n8n записывает исходные факты и результаты этапов. Итоговые показатели считаются в одной согласованной логике над данными Supabase. n8n не должен записывать независимые «готовые цифры для карточек», если их нельзя воспроизвести из сохранённых фактов.

Единственное отдельное происхождение данных — ручное исправление уполномоченного пользователя. Оно создаётся серверной частью дашборда как новое проверяемое событие в Supabase с автором, временем и причиной. Первоначальный результат n8n/ИИ не стирается. Разрешённые типы исправлений, capabilities и audit trail определены в [DASHBOARD_ADMIN](specs/DASHBOARD_ADMIN.md).

## Логические данные, нужные дашборду

Полный первичный словарь хранения закреплён в [DATA_DICTIONARY](DATA_DICTIONARY.md). Таблица ниже описывает удобные для дашборда логические данные/представления и не создаёт вторую модель истины. Например, пользовательская «обратная связь» собирается из исходящего действия и попыток доставки, а технические ошибки — из операций/попыток.

Окончательные SQL-имена, типы и способ реализации представлений появятся на техническом этапе. Рабочие коды ниже не переопределяют сущности DATA_DICTIONARY.

## Что n8n обязан записывать по этапам

| Этап процесса | Минимальная запись до следующего шага |
|---|---|
| Приём события | Внешний ID, источник, время, направление, менеджер и результат регистрации/дубля |
| Фильтрация | Клиентский/исключённый/пропущенный, стабильный код причины и версия правил |
| Получение аудио | Статус доступности, служебные метаданные временного файла и последующий факт удаления |
| Транскрибация | Версия текста, сегменты, роли и показатели качества |
| Анонимизация | Версия подготовленного текста; таблица соответствий остаётся в защищённой области |
| Анализ | Общий балл, применимые критерии, этапы, наблюдения, результат, доказательства и все использованные версии |
| Синхронизация CRM | Подтверждённый внешний результат отдельно от предположения ИИ |
| Доставка менеджеру | Созданное действие, попытки, подтверждённый/неизвестный итог |
| Ошибка | Этап, код, допустимость повтора и окончательное состояние |

Каждая логическая операция имеет устойчивый `operation_id` по [INTEGRATION_CONTRACTS](specs/INTEGRATION_CONTRACTS.md), а каждая фактическая попытка — отдельный `attempt_id`. Повтор одного события не создаёт второй звонок, анализ, CRM-факт или сообщение менеджеру.

## Согласованные представления для серверной части дашборда

Технически это могут быть PostgreSQL view, materialized view или ограниченные функции. Выбор будет сделан позднее. Смысл и формулы должны оставаться едиными.

| Представление | Назначение | Основные источники |
|---|---|---|
| `v_dashboard_obshchaya_kartina` | Общие звонки, оценённые, исключённые, пропущенные, средний балл, результаты | звонки, фильтрация, анализы, качество, результаты |
| `v_dashboard_menedzhery` | Строка показателей каждого менеджера | менеджеры, звонки, анализы, CRM, перезвоны |
| `v_dashboard_kriterii` | Средние баллы по применимым критериям и параметры речи | оценки критериев, метрики речи, анализы, качество |
| `v_dashboard_etapy` | Последний достигнутый этап и прохождение этапов | этапы звонка, звонки, анализы |
| `v_dashboard_oshibki` | Частота стабильных кодов ошибок и сильных сторон | наблюдения анализа, доказательства |
| `v_dashboard_zvonki` | Фильтруемый список и переход к карточке звонка | звонки и связанные сущности |
| `v_dashboard_rezultaty` | Предположение ИИ и подтверждение CRM раздельно | результаты ИИ, подтверждения CRM |
| `v_dashboard_kachestvo` | Надёжные, предварительные и технически неготовые анализы | качество обработки, ошибки, анализы |

Сервер дашборда применяет одну и ту же группу фильтров ко всем представлениям. Браузер не пересчитывает итоговые формулы самостоятельно.

## Общие фильтры

Фильтры действуют на все карточки, диаграммы, таблицы и переходы аналитических разделов:

- период;
- менеджер;
- отдел;
- источник;
- направление;
- первый/повторный звонок;
- результат;
- надёжность анализа;
- тип звонка.

Период определяется по времени начала события у источника, приведённому к часовому поясу компании. Граница задаётся как начало включительно, конец не включительно. Выбранные фильтры сохраняются при переходе между разделами и возврате из карточки звонка.

## Базовые правила расчёта

Полные формулы и знаменатели закреплены в [METRICS](specs/METRICS.md). Ни n8n, ни отдельная страница интерфейса не вводят собственную альтернативную формулу.

### Разложение всех звонков

Категории не должны накладываться друг на друга:

`все зарегистрированные логические звонки = оценённые клиентские разговоры + исключённые фильтром + пропущенные клиентские + ожидающие/технически не завершённые`.

Демонстрационный пример:

- всего — 312;
- оценено клиентских разговоров — 248;
- исключено фильтром — 46;
- пропущено клиентских — 18;
- ожидающих/технически незавершённых — 0.

Дубль события не входит в число логических звонков второй раз.

### Надёжность оценки

`nadezhno` означает одновременно:

- анализ структурно завершён;
- качество аудио/транскрипции прошло утверждённые проверки;
- роли МЕНЕДЖЕР/КЛИЕНТ назначены с допустимой надёжностью;
- нет незакрытого критического предупреждения или ручного оспаривания результата.

Иначе готовый анализ получает статус `predvaritelno` и видимую причину. Количество надёжных оценок не задаётся заранее и считается из фактических данных. Число 176 из демонстрационного макета не является требованием.

Средний официальный балл по умолчанию рассчитывается только по текущим действующим анализам со статусом `nadezhno`. Предварительные оценки видны отдельным числом и доступны через фильтр, но не смешиваются с официальным средним. Руководитель может открыть их отдельно.

### Оценки критериев

Среднее по критерию считается только по звонкам, где критерий применим. Значение «не применимо» не превращается в ноль. Каждый балл связан с версией методики и доказательствами.

### Доведение до этапа

Для каждого звонка сохраняются применимость и факт прохождения этапов:

1. приветствие;
2. выявление потребности;
3. презентация;
4. работа с возражением;
5. завершение сделки / целевое действие.

Возражение может отсутствовать и тогда не блокирует достижение целевого действия. Для менеджера показываются:

- количество и доля звонков, дошедших до каждого этапа;
- распределение по последнему достигнутому этапу;
- звонки, в которых обязательный применимый этап пропущен.

Это отдельный блок от оценки качества этапа. «Дошёл до презентации» не означает «хорошо провёл презентацию».

### Повторяющиеся ошибки

Ошибка имеет стабильный код, например `net_sleduyushchego_shaga`. Карточка показывает число уникальных звонков с этим кодом и долю от применимой выборки. Нажатие передаёт тот же код в список звонков; открываются только звонки с выбранной ошибкой, текущим периодом и остальными активными фильтрами.

### Результаты

ИИ-результат и подтверждение CRM не объединяются в один факт. Целевой результат ИИ считается по оценённым клиентским разговорам. Фактические замеры, встречи, счета, договоры и оплаты считаются только по подтверждениям CRM/человека.

### Пропущенные и перезвоны

Пропущенный клиентский звонок считается по подтверждённому статусу источника. Перезвон связывается по доверенному клиенту/сделке/телефону и окну компании. Неоднозначная связь не считается подтверждённым перезвоном.

Отдельного раздела «Пропущенные» в согласованной навигации нет. Показатели находятся в общей картине и карточке менеджера; нажатие открывает отфильтрованный список соответствующих звонков.

## Контрольные проверки будущей реализации

1. Сумма взаимоисключающих категорий объясняет общее число звонков за период.
2. Один и тот же фильтр даёт одинаковую выборку на карточке, диаграмме и в списке звонков.
3. Выбор менеджера меняет все показатели, этапы, ошибки, результаты и список звонков.
4. Нажатие на повторяющуюся ошибку показывает только звонки с её кодом.
5. Предварительный анализ не попадает в официальный средний балл.
6. «Не применимо» не снижает оценку критерия.
7. ИИ-результат не выдаётся за подтверждённую CRM продажу.
8. Дубль входного события не изменяет показатели второй раз.
9. Компания A не может получить строки, суммы или доказательства компании B.
10. Любая цифра раскрывается до списка звонков, а оценка — до цитаты/таймкода и версии анализа.
11. Выгрузка с теми же фильтрами совпадает с показателями на экране.
