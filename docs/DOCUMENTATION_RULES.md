# Правила документации

Цель: новая сессия должна продолжить одну небольшую задачу без необходимости читать старую переписку.

## Один источник для одного правила

README — навигация. WORKPLAN — порядок. PROJECT_STATE — короткая текущая точка. Они не должны становиться альтернативными спецификациями продукта.

## Типы записей

Всегда различай:

- **Требование** — обязательное поведение будущего продукта.
- **Принятое решение** — уже выбранное правило.
- **Параметр внедрения** — значение конкретной компании.
- **Гипотеза / кандидат** — требует тестирования, например Whisper.
- **Создано** — файл существует в GitHub.
- **Применено** — изменение выполнено в конкретной среде.
- **Проверено** — указан сценарий, среда/версия и фактический результат.

Не превращай кандидата в принятое решение без проверки.

## Постоянные ID

ID задачи не переиспользуется. Статусы:

- `[ ]` — не начато;
- `[~]` — в работе;
- `[x]` — критерий готовности проверен;
- `[!]` — пауза с указанной причиной.

Одна небольшая задача — одна сессия. Если пункт велик, до начала раздели его на подзадачи вида `DOC-03.1`, `DOC-03.2`. Родитель закрывается только после обязательных подзадач.

## Как менять требования без потерь

1. Прочитай основной документ и связанные резюме.
2. Сопоставь изменение с ранее согласованным требованием.
3. Не удаляй требование только из-за отсутствия технического решения.
4. Обнови основной документ и только необходимые ссылки/резюме.
5. Проверь, что новое правило не противоречит другим документам.
6. Проверь относительные ссылки, статусы, ID и отсутствие секретов.
7. Обнови WORKPLAN и PROJECT_STATE той же задачей.
8. Сохрани понятный commit и прочитай результат с GitHub.

Если принято новое решение вместо старого, актуальное правило явно записывается в основном документе. История остаётся в Git.

## Проверяемость

Для закрытия документационной задачи нужен наблюдаемый результат: файл создан или обновлён, обязательные темы покрыты, противоречий и битых ссылок нет.

Будущая рабочая задача не закрывается фразой «файл есть». Нужно отдельно подтверждать импорт, применение, запуск и рабочую проверку.

Результат анализа звонка должен быть логически воспроизводим по неизменяемому input manifest и правилам [VERSIONING](specs/VERSIONING.md); для внешних моделей отдельно фиксируются доступные ограничения вычислительной воспроизводимости.

## GitHub и исполнители

Перед изменением проверь ветку и исходный SHA. Для одного набора файлов назначается один исполнитель. Не применять force push и не перезаписывать более новые изменения.

Окончательный commit текущего изменения не записывается внутрь самого себя: PROJECT_STATE хранит ID и состояние, а SHA передаётся в сообщении handoff.

## Публичность

В публичном репозитории разрешены общие требования, шаблоны и обезличенные подтверждения.

Запрещены реальные аудиозаписи, транскрипции клиентов, персональные данные, токены, пароли, закрытые документы компании, дампы и резервные копии.

PROJECT_STATE должен оставаться коротким. Полная история изменений хранится в Git.
