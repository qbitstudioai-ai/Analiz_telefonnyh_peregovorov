# Размещение анализа звонков на российском сервере

Статус: базовая архитектурная позиция для будущей реализации. Документ не подтверждает, что сервер уже подготовлен, а сервисы установлены или испытаны.

## Принятое решение

Основные компоненты продукта размещаются на одном российском сервере:

- n8n как оркестратор процесса;
- одна self-hosted установка Supabase/PostgreSQL и pgvector;
- сервис WhisperX с faster-whisper для распознавания речи;
- pyannote или другой проверенный локальный модуль диаризации;
- локальный модуль определения ролей и псевдонимизации;
- серверные части и веб-интерфейсы дашбордов;
- reverse proxy, технические журналы и мониторинг в утверждённых границах.

WhisperX, faster-whisper и pyannote являются базовыми кандидатами, а не автоматически принятыми победителями. Их качество, скорость, лицензии, модели и нагрузка проверяются по единому протоколу [TRANSCRIPTION_AND_PRIVACY](specs/TRANSCRIPTION_AND_PRIVACY.md); до фактического теста конкретный движок не считается выбранным для production.

Один физический сервер не означает один процесс. Компоненты разворачиваются как отдельные сервисы или контейнеры с разными доступами и лимитами. При росте нагрузки транскрибацию можно вынести на отдельный российский GPU-сервер без изменения CORE.

## Важная граница российского контура

Исходное аудио, исходная транскрипция и таблица соответствия псевдонимов не должны покидать российский контур.

Базовый вариант допускает внешние API:

- DeepSeek или совместимый провайдер — анализ обезличенного разговора;
- Qwen Embedding API или совместимый провайдер — векторы для разрешённых фрагментов знаний и обезличенных запросов.

Поэтому схема является **российским размещением основной инфраструктуры**, но не полностью закрытым контуром обработки. Если договор, закон или политика компании запрещают даже обезличенный внешний вызов, LLM и embedding-модель заменяются локальными сервисами. Такая замена не должна менять CORE, данные звонка и правила оценки.

## Движение данных звонка

~~~mermaid
flowchart TD
    A["CRM / телефония"] --> B["n8n на российском сервере"]
    B --> C["Supabase: событие и состояние"]
    B --> D["Локальная транскрибация и роли"]
    D --> E["Локальная псевдонимизация"]
    E --> F["Внешняя LLM: обезличенный пакет"]
    F --> B
    B --> C
    C --> G["Сервер дашборда компании"]
~~~

Обязательный порядок:

1. Зарегистрировать событие и защититься от дубля.
2. Проверить фильтры; не скачивать и не анализировать заведомо исключённый звонок.
3. Временно получить аудио внутри российского контура.
4. Локально выполнить транскрибацию, диаризацию, назначение ролей и оценку качества.
5. Сохранить версию результата и локально псевдонимизировать текст.
6. Передать внешней LLM только разрешённый обезличенный контекст, версию промта, правила оценки и очищенные знания.
7. Проверить ответ CORE и сохранить версионированный анализ с доказательствами.
8. Как только подтверждены все локальные этапы, которым нужен звук, удалить временное аудио и сохранить подтверждение удаления по [AUDIO_RETENTION](specs/AUDIO_RETENTION.md); для удаления не требуется ждать LLM, дашборд или доставку обратной связи.
9. Продолжить анализ обезличенного текста, сделать результат доступным серверу дашборда и отдельно выполнить доставку обратной связи.

Внешняя LLM не получает аудиофайл, ФИО, телефоны, email, секреты, имя schema, права, адресата доставки или таблицу соответствия псевдонимов. Она предлагает оценку и рекомендации, но не подтверждает факт продажи и не отправляет сообщение менеджеру самостоятельно.

## История клиента и персональные данные

Связь нескольких звонков с одним клиентом хранится локально по доверенным идентификаторам CRM/телефонии. Для анализа продолжения разговора формируется краткий обезличенный контекст предыдущих звонков. Полный сырой архив не отправляется во внешнюю модель без необходимости.

Таблица вида `PERSON_01 → реальный клиент` хранится только в защищённой области российского Supabase. Дашборд объединяет разрешённые персональные поля и AI-анализ на серверной стороне после проверки прав; браузер и LLM не выполняют это объединение.

## RAG и embeddings

Supabase хранит оригинал разрешённого документа, версии, фрагменты, состояние публикации и вектора. Embedding API не является базой данных.

Текст каждого фрагмента, отправленного во внешний embedding API, покидает российский сервер. Поэтому:

- персональные данные удаляются или заменяются до отправки;
- коммерчески чувствительные фрагменты отправляются только при явном разрешении политики внедрения;
- при запрете внешней передачи используется локальная embedding-модель;
- анализ получает только опубликованные знания своей компании;
- результат анализа хранит точную версию использованных знаний.

## Изоляция компаний

Одна установка Supabase обслуживает несколько компаний, но разделение является обязательным проверяемым правилом:

- у каждой компании и среды отдельная schema одинаковой структуры;
- у n8n, сервисов обработки и серверной части дашборда отдельные ограниченные роли;
- общий `postgres`, `service_role` и административные ключи не используются в обычной работе;
- schema не выбирается из события источника, ответа LLM или параметра браузера;
- Credentials, источники, фильтры, сотрудники, критерии оценки, знания и дашборд компании отделены;
- test и production не используют одни токены, входы и роли;
- отрицательные проверки доказывают, что компания A не читает и не меняет данные компании B.

Подробные права будут закреплены в будущей задаче DOC-10.

## Что и где хранится

| Данные | Постоянное место | Во внешний AI API |
|---|---|---|
| Событие звонка и подтверждённые ID | Schema компании в Supabase | Только технический ID без персональных данных при необходимости |
| Аудио | У источника; локальная копия только по [AUDIO_RETENTION](specs/AUDIO_RETENTION.md) | Никогда |
| Исходная транскрипция и сегменты | Supabase компании по будущей политике хранения | Никогда в исходном виде |
| Таблица соответствия псевдонимов | Защищённая область российской БД | Никогда |
| Обезличенная транскрипция | Supabase с версией | Да, минимально необходимая часть |
| Анализ, оценка и доказательства | Supabase | Возвращаются внешним API и проверяются CORE |
| Документы знаний и embeddings | Supabase/pgvector | Только разрешённые очищенные фрагменты для embedding API |
| Секреты интеграций | Credentials/серверные секреты | Никогда |

n8n не является основной БД, постоянным хранилищем аудио или единственной памятью процесса. Значимое состояние сохраняется в Supabase до следующего затратного или внешнего действия.

## Заменяемые адаптеры

CORE использует согласованные интерфейсы, а не жёсткую зависимость от бренда:

- сервис транскрибации и диаризации;
- `LLM adapter`: DeepSeek, другая внешняя LLM или локальная модель;
- `Embedding adapter`: Qwen, другой API или локальная модель;
- источники звонков, CRM и каналы обратной связи;
- серверный API дашборда.

Смена провайдера требует испытаний качества, форматов, лимитов, стоимости и политики данных, но не переписывания жизненного цикла звонка.

## Что необходимо проверить до реализации

- ресурсы CPU, RAM, GPU, диска и запас мощности при одновременной транскрибации;
- качество русской телефонной речи, диаризации и назначения ролей;
- лицензии выбранных моделей и компонентов;
- резервное копирование Supabase и проверенное восстановление;
- закрытие PostgreSQL/Studio от публичного доступа, TLS и правила исходящего трафика;
- перечень данных, разрешённых каждому внешнему провайдеру;
- сроки хранения исходной и обезличенной транскрипции, журналов и временного аудио;
- очистку execution data n8n, мониторинг очередей, ошибок, GPU и свободного места;
- отдельные test/production-доступы и безопасный выпуск;
- сценарий переноса WhisperX на отдельный российский сервер без потери состояния.

До этих проверок схема считается архитектурным решением, а не доказанной production-готовностью.
