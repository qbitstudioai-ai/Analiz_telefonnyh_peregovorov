# DB-03 — конфигурации и общая база знаний

Статус: создано в GitHub, **не применено к Supabase**.

Зависимости: DB-01, DB-02.

## Цель

Создать физическую versioned-модель для:

- prompt;
- methodology/criteria/stages;
- filter rules;
- канонических knowledge documents;
- document versions;
- fragment versions;
- embedding versions/provenance;
- immutable knowledge publications;
- product scope одного общего источника знаний.

DB-03 не реализует фактические runtime roles/grants/RLS — это DB-07. Не выбирает embedding-модель, размер pgvector и ranking — это AI-03/последующая migration после измерений.

## Файлы

- `supabase/migrations/003_config_knowledge.sql`;
- `supabase/verify/003_config_knowledge_verify.sql`;
- `supabase/rollback/003_config_knowledge_rollback.sql`.

## Физические сущности

Migration создаёт 13 таблиц:

1. `prompt_versions`;
2. `methodology_versions`;
3. `methodology_criteria`;
4. `methodology_stages`;
5. `filter_rule_versions`;
6. `knowledge_documents`;
7. `knowledge_document_versions`;
8. `knowledge_fragments`;
9. `knowledge_embeddings`;
10. `knowledge_publications`;
11. `knowledge_publication_documents`;
12. `knowledge_publication_fragments`;
13. `knowledge_publication_fragment_products`.

Дополнительно создаётся внутренний published-only source view `v_runtime_knowledge_fragments`.

**Его нельзя напрямую выдавать продуктовым runtime-ролям.** DB-07 должен поверх него сделать product-scoped ограниченный доступ.

## Конфигурации анализа

### Prompt

Каждая версия имеет:

- family;
- version number;
- predecessor;
- exact text/hash;
- draft/ready/active/superseded/invalidated;
- validation;
- actor/change reason;
- activation time.

Новая строка обязана начинаться как `draft`. После выхода из draft смысловые поля нельзя менять in-place.

Active version нельзя вернуть в draft.

### Methodology

Версия methodology отдельно хранит общий scoring/result config, а criteria/stages — дочерними строками.

Criteria/stages можно менять только пока parent methodology = `draft`.

После ready/active изменения требуют новой methodology version.

### Filter rules

`filter_rule_versions` становится физическим FK-источником для уже существующего `filter_decisions.filter_rules_version_ref`.

Это означает: решение фильтра теперь не может ссылаться на произвольную несуществующую версию правил.

## Канонические знания

### Документ

`knowledge_documents` — один канонический бизнес-материал.

`knowledge_document_versions` — версии его содержимого.

Это позволяет нескольким продуктам использовать один документ без копирования самого документа.

Document version хранит:

- exact content/hash;
- source/version metadata;
- validation;
- editorial state;
- external embedding policy;
- actor/change reason;
- predecessor/current/invalidation.

После ready/publication semantic content нельзя менять — нужна новая version.

### Fragment

`knowledge_fragments` принадлежит exact document version.

Хранит:

- stable fragment family;
- fragment version;
- order;
- chunking version;
- normalization version;
- text/hash;
- source locator;
- validation/version state.

Изменение chunking или текста требует новой fragment version.

### Embedding

`knowledge_embeddings` всегда привязан к exact `fragment_id`.

Сохраняются:

- provider/model/model version;
- config version/config;
- dimensions;
- input fragment hash;
- vector representation;
- local/external API flag;
- validation/state;
- provenance/actor.

Ready embedding нельзя переписать in-place.

### Почему сейчас `real[]`, а не `vector(N)`

Размер embedding-вектора зависит от реально выбранной модели.

AI-03 ещё не выполнен, поэтому DB-03 сознательно не выдумывает dimension и pgvector index.

Сейчас `real[]` используется как временный физический контейнер с обязательным `dimensions` и CHECK `cardinality(vector_data) = dimensions`.

После выбора embedding-модели отдельная migration сможет добавить pgvector/индекс, не меняя fragment/version provenance.

## Knowledge publication

Publication — immutable manifest, а не запрос «все последние строки».

`knowledge_publications` фиксирует:

- family/version/predecessor;
- draft/ready/published/superseded/archived/invalidated;
- validation;
- manifest hash;
- actor/source operation;
- publication time;
- current marker.

Состав хранится отдельными exact membership-таблицами:

- exact document versions;
- exact fragments;
- exact embedding, если обязателен;
- explicit product scopes.

## Product scope

Один fragment может быть разрешён одновременно:

- `call_analysis`;
- `initial_contact_bot`;
- другому будущему продукту.

Это создаёт две строки product scope, но **не две копии документа/fragment**.

Таким образом выполняется DOC-17: канонический источник общий, runtime identities продуктов независимы.

## Publication activation gate

Publication нельзя вставить сразу как published.

Порядок:

1. создать draft/ready publication;
2. добавить exact membership;
3. добавить product scopes;
4. validation;
5. отдельным UPDATE активировать published/current.

Перед activation БД проверяет:

- есть exact documents;
- есть exact fragments;
- документы ready + validated;
- каждый document имеет fragment;
- fragments validated и не invalidated;
- required embedding существует и ready/validated;
- embedding input hash совпадает с exact fragment hash;
- внешний embedding разрешён exact document version;
- каждый fragment имеет хотя бы один product scope.

После publication membership менять нельзя.

Published manifest/provenance нельзя вернуть в draft/ready или переписать in-place.

## Runtime source view

`v_runtime_knowledge_fragments` содержит только:

- current published publication;
- validated non-invalidated docs/fragments;
- valid required embeddings;
- explicit product_code;
- exact publication/document/fragment/embedding IDs и provenance.

Но этот view является **внутренним источником**, а не готовым permission boundary.

DB-07 должен запретить unrestricted SELECT для product runtime roles и дать доступ только через product-scoped restricted view/function/role.

## Verification

`003_config_knowledge_verify.sql` работает внутри транзакции и завершает её `ROLLBACK`.

Он проверяет:

- 13 DB-03 tables + runtime source view;
- невозможность вставить prompt сразу active;
- activation prompt и запрет изменить active content;
- запрет active → draft;
- methodology children доступны в draft и frozen после выхода из draft;
- filter decision обязан ссылаться на существующую filter version;
- один canonical document/fragment используется двумя product scopes;
- draft publication отсутствует в runtime;
- published publication раскрывает exact publication/document/fragment/embedding provenance;
- published membership immutable;
- published document immutable;
- publication нельзя вернуть в ready;
- publication без product scope блокируется;
- forbidden external embedding блокирует publication;
- embedding с hash, не совпадающим с exact fragment, блокирует publication.

## Rollback

`003_config_knowledge_rollback.sql`:

- оставляет DB-01 и DB-02;
- удаляет DB-03 view/tables/functions/types;
- снимает FK DB-03 с `filter_decisions`;
- отказывается запускаться, если DB-03 неполон;
- отказывается запускаться, если уже появились later/unknown relations.

После DB-04 и следующих migrations этот rollback нельзя выполнять без отката зависимой цепочки.

## Статическая проверка

До реального PostgreSQL-run подтверждено:

- SQL lexical structure сбалансирована;
- migration создаёт 13 tables и 1 view;
- 9 trigger-functions имеют уникальные имена;
- отсутствует executable production schema DDL;
- отсутствует executable `service_role`;
- отсутствуют `bytea/blob`;
- record `NEW/OLD` для DELETE обрабатывается явно;
- config lifecycle имеет draft-first guard;
- publication нельзя reopen в draft/ready;
- activation проверяет product scope, embedding policy и fragment hash;
- migration не выдаёт GRANT runtime-ролям;
- типовых реальных секретов в файлах задачи не должно быть; это дополнительно проверяется перед закрытием.

## Риски и отложенные решения

- SQL ещё не запускался на PostgreSQL/Supabase;
- реальная permission isolation будет только в DB-07;
- `real[]` не является финальной vector-search реализацией;
- embedding model/dimensions/index/ranking ещё не выбраны;
- publication validation workflow в сервисе/n8n ещё не создан;
- actor/capability audit физически завершится DB-05/DB-07;
- реальные документы компании в GitHub не добавляются.
