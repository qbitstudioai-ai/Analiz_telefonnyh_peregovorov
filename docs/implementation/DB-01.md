# DB-01 — базовая migration приёма и надёжности

Статус: создано в GitHub, **не применено к Supabase**.

Исходная точка реализации: `main` после GATE-01 и активации `WORKPLAN_IMPLEMENTATION.md`.

## Цель

Создать первый физический слой test/локального Supabase для данных, которые нужны ещё до транскрибации и анализа:

- события источника;
- логические звонки;
- менеджеры;
- связи звонков;
- решения фильтра;
- логические операции;
- попытки операций;
- metadata временных аудиоартефактов.

DB-01 не создаёт транскрипции, знания, analyses, evidence, dashboard views, runtime roles/RLS и production объекты. Они идут отдельными задачами.

## Файлы

- `supabase/migrations/001_base_ingest_reliability.sql` — основной migration;
- `supabase/verify/001_base_ingest_reliability_verify.sql` — безопасная самопроверка с синтетическими данными внутри транзакции и последующим `ROLLBACK`;
- `supabase/rollback/001_base_ingest_reliability_rollback.sql` — guarded rollback для test-схемы.

## Test-контур

Физическое решение DB-01:

- одна PostgreSQL schema представляет один контур `компания + среда`;
- для шаблонной локальной проверки используется нейтральная schema `atp_test`;
- `atp_test` не является production и не является названием конкретной компании;
- DB-07 отдельно реализует runtime roles/grants/RLS и фактические cross-company/test-prod negative tests.

Migration специально отказывается запускаться, если `atp_test` уже существует. Это защищает от слепого повторного запуска поверх неизвестного состояния.

## Что создаёт migration

В `atp_test` создаются 8 первичных таблиц:

1. `managers` — доверенные сотрудники;
2. `calls` — один логический звонок, не webhook;
3. `call_events` — полученные сигналы источника;
4. `operations` — идемпотентные логические операции;
5. `operation_attempts` — конкретные попытки операций;
6. `filter_decisions` — версионируемые решения фильтра;
7. `call_links` — доверенные связи звонка с прежним звонком/CRM-сущностью;
8. `temporary_audio_artifacts` — только metadata временного локального аудио.

Дополнительно создаются enum-типы, indexes, ограничения и служебная trigger-функция `set_updated_at()`.

## Ключевые инварианты

### Дубль события не создаёт второй логический звонок

У `calls` есть server-derived `call_identity_key`, уникальный внутри `source_adapter_code + connection_ref`.

У `call_events` есть `event_identity_key`.

Первое не-дублирующее событие с такой идентичностью уникально. Повторный receipt допускается только как `decision = duplicate` и должен ссылаться через `duplicate_of_event_id` на ранее известное событие.

Это сохраняет сам факт повторного получения, но не создаёт второй call.

### Retry не создаёт вторую логическую operation

`operations` имеет уникальность:

`call_id + operation_type + idempotency_key`.

Безопасный повтор создаёт новую строку `operation_attempts` с тем же `operation_id`, а не новую эквивалентную operation.

### Operation и результат относятся к одному звонку

Составные foreign keys не позволяют:

- привязать filter decision к operation другого call;
- сделать current filter decision одного call решением другого call;
- привязать временный audio artifact к acquisition operation другого call.

### Состояния operation отделены от transport

Хранятся канонические состояния:

- `not_started`;
- `in_progress_unconfirmed`;
- `succeeded`;
- `failed_retryable`;
- `failed_requires_fix`;
- `outcome_unknown`.

Transport result попытки хранится отдельно и не доказывает business success.

### Аудио не хранится постоянно

`temporary_audio_artifacts` содержит только:

- server-generated local artifact ref;
- размер/длительность и integrity metadata;
- acquisition state;
- delete deadline;
- cleanup/deletion status;
- error code удаления.

В DB-01 нет `bytea`/blob-колонки для звука.

## Почему raw payload источника не сохраняется

DB-01 сознательно не добавляет колонку для полного webhook payload.

Сохраняются нормализованные trusted refs и `safe_metadata`.

Это уменьшает риск бессрочного хранения телефонов, секретов и лишних данных. Если конкретному адаптеру позже понадобится дополнительное происхождение, оно добавляется явно и проходит privacy/retention проверку.

## Проверка после будущего применения

Порядок:

1. применить `supabase/migrations/001_base_ingest_reliability.sql` **только в test/локальной БД**;
2. убедиться, что migration завершился без ошибки;
3. запустить `supabase/verify/001_base_ingest_reliability_verify.sql`;
4. verification должен завершиться сообщением `DB-01 verification PASS...`;
5. verification сам откатывает созданные синтетические строки;
6. только после фактического результата обновить статус «применено/проверено».

Verification проверяет:

- наличие всех 8 таблиц;
- отсутствие `bytea`;
- обычный call/event;
- duplicate receipt без второго логического call;
- блокировку второго non-duplicate event identity;
- idempotency операции;
- operation attempts;
- current filter decision;
- запрет cross-call operation/filter binding;
- metadata временного аудио;
- запрет отрицательной длительности;
- обязательный code для rejected event.

## Rollback

`supabase/rollback/001_base_ingest_reliability_rollback.sql`:

- предназначен только для test;
- удаляет schema `atp_test` целиком;
- **откажется запускаться**, если не найдены все 8 DB-01 таблиц;
- **откажется запускаться**, если в schema уже появились неизвестные/later tables;
- не удаляет extension `pgcrypto`, потому что он может быть общим для других компонентов.

После DB-02 и следующих migrations откатывать DB-01 этим скриптом нельзя: сначала нужен отдельный rollback всей зависимой цепочки.

## Риски

- физические имена и enum-коды теперь становятся частью реализации и должны меняться только миграциями;
- DB-01 ещё не доказывает изоляцию runtime roles — это DB-07;
- migration ещё не запускался на реальном Supabase/PostgreSQL;
- синтаксическая статическая проверка не заменяет выполнение PostgreSQL;
- `safe_metadata` и `safe_context` сами по себе не делают данные безопасными: адаптер/CORE обязан не писать туда секреты и лишний raw content;
- `atp_test` является шаблонным test-контуром; механизм provisioning нескольких company schemas будет определён отдельно.

## Действия Павла

**Сейчас ничего запускать не нужно.**

DB-01 сначала проходит статическую проверку в GitHub. Фактическое применение SQL запланировано отдельной задачей DB-08 после завершения базовой цепочки migrations и прав test-контура.

Если понадобится ранняя проверка migration на отдельной пустой test Supabase, ChatGPT отдельно даст Павлу один полный SQL и точный порядок запуска. Без такого отдельного задания запускать файл не требуется.

## Граница статуса

На текущем этапе допустимо сказать:

- SQL создан;
- SQL записан в GitHub;
- verification и rollback созданы.

Пока нельзя говорить:

- SQL применён;
- schema создана в Supabase;
- constraints реально сработали в PostgreSQL;
- DB-01 проверен на сервере;
- test Supabase готов;
- production готов.
