# DB-07 — изоляция и права test

Статус: создано в GitHub, **не применено к Supabase**.

Зависимости: DB-01—DB-06.

## Цель

Создать физическую модель доступа для одного test-контура:

- одна PostgreSQL schema = одна компания + одна среда;
- отдельные capability-роли по обязанностям;
- raw/mapping доступны только privacy-роли;
- обычный CORE работает только с псевдонимизированными данными;
- knowledge runtime читает только опубликованные знания своего продукта;
- dashboard читает только подготовленные views;
- ручные corrections/disputes идут через ограниченные функции;
- monitoring не получает содержание разговоров;
- PUBLIC не получает автоматический доступ к функциям/таблицам схемы.

DB-07 не создаёт реальные login/password Credentials. Они должны появляться только в конкретном test-контуре вне GitHub.

## Файлы

- `supabase/migrations/007_access_isolation.sql`;
- `supabase/verify/007_access_isolation_verify.sql`;
- `supabase/rollback/007_access_isolation_rollback.sql`.

## Решение по границе компании

В шаблоне физическая граница уже выбрана в DB-01:

**одна schema = одна компания + одна среда**.

Поэтому DB-07 не добавляет фиктивный tenant RLS внутри `atp_test`.

Причина:

- внутри одной schema нет tenant/company column;
- policy вида `USING (true)` ничего не изолирует;
- такая RLS создала бы ложное ощущение защиты.

Cross-company/test-production isolation строится на:

1. отдельной schema;
2. отдельной Credential/login identity;
3. capability-role только своего contour;
4. отсутствии `CREATE` в schema у runtime roles;
5. отсутствии произвольного schema name в runtime functions;
6. отрицательных cross-schema checks.

Если в будущем физическая модель сменится на shared schema + tenant column, потребуется отдельное RLS-решение и новая migration.

## Capability roles

Создано 8 PostgreSQL ролей.

Все роли:

- `NOLOGIN`;
- `NOSUPERUSER`;
- `NOCREATEDB`;
- `NOCREATEROLE`;
- `NOREPLICATION`;
- `NOBYPASSRLS`.

### atp_test_orchestrator

Назначение: n8n/runtime orchestration.

Разрешено:

- managers/calls/events;
- operations/attempts;
- filter decisions;
- call links;
- temporary audio metadata;
- trusted CRM confirmations;
- callback links;
- outgoing actions;
- delivery attempts;
- читать metadata privacy/quality/analysis.

Запрещено:

- raw transcript;
- raw transcript segments;
- pseudonym reverse mapping;
- knowledge administration;
- произвольный schema CREATE.

### atp_test_privacy

Назначение: transcription/privacy processing.

Это единственная обычная runtime capability, которой разрешены:

- `raw_transcripts`;
- `transcript_segments`;
- `pseudonym_mappings`.

Также она может создавать/обновлять:

- role assignments;
- pseudonymized transcripts/segments;
- privacy packages;
- processing quality;
- speech metrics;
- свои operations/attempts.

Она не получает knowledge/dashboard access.

### atp_test_core

Назначение: analysis/evidence CORE.

Разрешено:

- calls/managers metadata;
- pseudonymized transcript/segments;
- privacy package;
- processing quality/speech metrics;
- prompt/methodology;
- product-scoped published knowledge;
- analysis/evidence create/update;
- свои operation records.

Запрещено:

- raw transcript;
- raw segment;
- reverse pseudonym mapping;
- direct base knowledge/draft access.

### atp_test_knowledge_call_analysis

Назначение: read-only knowledge reader для продукта анализа звонков.

Разрешён только:

`v_knowledge_call_analysis_runtime`.

Нет SELECT на base knowledge tables.

Нет INSERT/UPDATE/publish прав.

### atp_test_knowledge_admin

Назначение: отдельная привилегированная test capability для config/knowledge administration.

Разрешено:

- prompt/methodology/filter configs;
- documents/document versions;
- fragments/embeddings;
- publication manifest/membership;
- audit insert/read.

Не разрешено:

- calls;
- raw/pseudonym mapping;
- обычное использование как runtime analysis role.

Immutable/published guards DB-03 продолжают действовать.

### atp_test_dashboard

Назначение: read-only dashboard server capability.

Разрешено:

- DB-06 dashboard views;
- DB-06 metric functions;
- safe pseudonymized transcript view;
- safe conversation evidence;
- exact used knowledge evidence.

Запрещено:

- direct business-table write;
- raw transcript;
- reverse mapping;
- base knowledge;
- direct correction insert/update.

### atp_test_correction_operator

Назначение: отдельная backend capability для разрешённых disputes/corrections.

Разрешено:

- читать safe dashboard/evidence;
- читать dispute/correction/audit history;
- вызывать 4 контролируемые write functions.

Нет direct INSERT/UPDATE на correction/dispute tables.

### atp_test_monitoring

Назначение: технический monitoring.

Разрешено только:

- `v_monitoring_calls`;
- `v_monitoring_operations`.

Views не содержат:

- transcript text;
- pseudonym mapping;
- knowledge content;
- message body;
- CRM JSON payload.

## PUBLIC boundary

Migration выполняет:

- `REVOKE ALL ON SCHEMA atp_test FROM PUBLIC`;
- `REVOKE ALL ON ALL TABLES ... FROM PUBLIC`;
- `REVOKE ALL ON ALL SEQUENCES ... FROM PUBLIC`;
- `REVOKE ALL ON ALL FUNCTIONS ... FROM PUBLIC`.

Это особенно важно для PostgreSQL functions, потому что новые функции по умолчанию могут иметь PUBLIC EXECUTE.

Также меняются default privileges владельца migration:

- будущие tables/sequences не получают ambient PUBLIC grants;
- будущие functions в `atp_test` не получают PUBLIC EXECUTE.

Каждый новый runtime grant всё равно должен добавляться явно отдельной migration.

## Safe views

Создано 6 security-barrier views.

### v_knowledge_call_analysis_runtime

Источник:

`v_runtime_knowledge_fragments`.

Дополнительный fixed filter:

`product_code = 'call_analysis'`.

Поэтому reader:

- видит только published/current validated runtime knowledge;
- не видит drafts;
- не видит другие product scopes;
- не может edit/publish.

### v_dashboard_safe_transcript_segments

Показывает только pseudonymized segments, которые:

- принадлежат реальному privacy package;
- включены в exact package segment membership;
- package имеет `privacy_status='passed'`;
- package не invalidated.

Raw text и mapping отсутствуют.

### v_dashboard_evidence_conversation

Разрешённый dashboard evidence:

- exact analysis/evidence;
- exact privacy package;
- exact pseudonymized segment;
- quote snapshot;
- time boundaries;
- business role;
- safe pseudonymized segment text.

### v_dashboard_evidence_knowledge

Показывает knowledge только когда fragment реально был:

- exact `analysis_knowledge_input`;
- exact evidence reference.

Dashboard не получает browse-доступ ко всей knowledge base.

### v_monitoring_calls

Только технические call states/время/source.

### v_monitoring_operations

Только:

- operation type/state;
- safe error class/code;
- attempt counts;
- unknown/retryable/requires-fix flags;
- timestamps.

## Controlled write functions

Создано 4 `SECURITY DEFINER` functions.

У всех жёстко задан:

`search_path = pg_catalog, atp_test`.

Runtime роли не имеют `CREATE` в schema, поэтому search_path нельзя подменить своим объектом.

### dashboard_open_analysis_dispute

Создаёт:

- open dispute;
- audit event.

Проверяет, что analysis принадлежит call.

Claim/evidence same-analysis дополнительно защищены FK DB-05.

### dashboard_propose_correction

Создаёт только `proposed` correction.

Поддерживает typed target:

- manager;
- role assignment;
- transcript;
- analysis;
- business confirmation;
- callback link;
- outgoing action.

Target ownership своего call проверяется FK/дополнительной проверкой manager.

Создаёт audit event.

### dashboard_resolve_analysis_dispute

Допустимый финал:

- resolved;
- rejected.

Изменение проходит существующий immutable lifecycle guard DB-05.

Создаёт audit event.

### dashboard_finalize_correction

Допустимый финал:

- applied;
- rejected.

Applied требует `apply_operation_id`.

DB-05 trigger дополнительно требует, чтобы operation:

- относилась к тому же call;
- была `succeeded`.

Создаёт audit event.

## Почему dashboard role сама не получает write functions

`atp_test_dashboard` — read-only.

Write functions выдаются только:

`atp_test_correction_operator`.

Это позволяет backend использовать разные Credentials/capabilities для:

- обычного просмотра;
- разрешённого административного действия.

Browser не получает ни одну из этих DB Credentials.

## Verification

`007_access_isolation_verify.sql` создаёт только внутри test transaction два probe contour:

- `atp_test_isolation_probe`;
- `atp_prod_probe`.

В конце весь verify делает `ROLLBACK`, поэтому probe schemas не остаются.

Проверяется:

### Role safety

У всех 8 ролей:

- NOLOGIN;
- no superuser;
- no create DB;
- no create role;
- no replication;
- no bypass RLS.

Также verify требует, чтобы на момент проверки к capability roles ещё не были подключены реальные member/login roles.

### Schema isolation

Для каждой роли:

positive control:

- есть USAGE на `atp_test`.

Negative controls:

- нет CREATE на `atp_test`;
- нет USAGE/SELECT на другой test probe schema;
- нет USAGE/SELECT на production probe schema.

### PUBLIC access

Проверяется:

- PUBLIC не имеет table/view grants;
- PUBLIC не имеет EXECUTE ни на одной функции `atp_test`;
- default privileges не вернут PUBLIC EXECUTE будущим функциям владельца migration.

### Destructive access

Ни одной capability-role не выданы:

- DELETE;
- TRUNCATE.

### Role matrix

Verify отдельно проверяет positive и negative controls для:

- orchestrator;
- privacy;
- CORE;
- product knowledge reader;
- knowledge admin;
- dashboard;
- correction operator;
- monitoring.

### Security-definer boundary

Проверяется:

- 4 функции имеют `SECURITY DEFINER`;
- correction operator имеет EXECUTE;
- ordinary dashboard не имеет EXECUTE;
- search_path закреплён;
- safe views сохранили `security_barrier=true`.

### Privacy/knowledge boundary

Проверяется:

- dashboard/core/orchestrator не имеют raw/mapping SELECT;
- privacy имеет необходимые raw/mapping права;
- knowledge reader не видит base/draft tables;
- dashboard knowledge evidence идёт через exact-input view.

### Secrets

Verify отказывается пройти, если в business schema появляется колонка с именем, содержащим:

- password;
- token;
- secret;
- credential.

Реальные Credentials должны храниться вне этой schema.

## Что verify не доказывает до DB-08

До фактического запуска PostgreSQL нельзя утверждать:

- CREATE ROLE разрешён конкретной test Supabase identity;
- GRANT/REVOKE реально применились;
- security-barrier views реально выполняются;
- отрицательные privilege checks реально PASS;
- Supabase/API configuration не добавляет внешний обход;
- реальные login Credentials разделены по компаниям/test-prod;
- dashboard backend использует правильную Credential;
- n8n использует правильную Credential.

Это проверяется фактически на DB-08 и последующих integration tasks.

## Rollback

`007_access_isolation_rollback.sql`:

1. проверяет наличие 8 DB-07 roles;
2. проверяет наличие 6 DB-07 views;
3. отказывается запускаться при later/unknown relations;
4. **отказывается**, если capability roles уже выданы реальным member/login roles;
5. снимает object grants;
6. удаляет 4 DB-07 functions;
7. удаляет 6 safe views;
8. восстанавливает pre-DB-07 PUBLIC EXECUTE для функций;
9. восстанавливает соответствующий default function privilege;
10. удаляет 8 NOLOGIN roles.

Таким образом случайный rollback после подключения test Credentials не молча ломает runtime access.

## Статическая проверка

Подтверждено по GitHub:

- migration: 8 roles / 6 views / 4 controlled functions;
- rollback: тот же набор roles/views/functions;
- все роли объявлены NOLOGIN и без broad role attributes;
- migration/rollback object sets совпадают;
- SQL lexical structure сбалансирована;
- production schema DDL отсутствует;
- plaintext password отсутствует;
- `service_role` не используется;
- `bytea/blob` отсутствуют;
- признаки типовых реальных секретов не найдены;
- rollback не использует CASCADE.
