# DB-07 — изоляция и права schema `shablon_analiz_telefonnyh_peregovorov`

Статус: SQL создан и усиленно статически проверен; **следующая migration для фактического применения в DB-08B**.

Зависимости: DB-01—DB-06.

Канонический комплект DB-07:

- `supabase/migrations/007_access_isolation.sql`;
- `supabase/verify/007_access_isolation_verify.sql`;
- `supabase/rollback/007_access_isolation_rollback.sql`.

## Цель

Физически разделить обязанности сервисов одного контура `shablon_analiz_telefonnyh_peregovorov` и подготовить проверяемую границу доступа:

- одна PostgreSQL schema = одна компания + одна среда;
- отдельная Credential должна соответствовать одному contour;
- runtime roles не получают широких административных прав;
- raw transcript и pseudonym mapping отделены от dashboard/CORE;
- runtime knowledge видит только active/published разрешённый scope;
- dashboard читает только подготовленные safe views;
- admin actions идут через ограниченные audited functions;
- monitoring получает технические состояния без содержимого разговоров;
- PUBLIC не является скрытым путём доступа.

Реальные LOGIN/password Credentials DB-07 **не создаёт**. Они должны создаваться вне GitHub после фактической проверки DB-08B.

## Почему здесь есть RLS, но это не tenant-RLS

Основная межфирменная граница остаётся:

**schema + отдельная Credential = company + environment contour**.

Внутри `shablon_analiz_telefonnyh_peregovorov` нет tenant/company column, поэтому RLS не используется как способ разделить компании.

Но для трёх особенно чувствительных таблиц RLS используется как **defense-in-depth role gate**:

- `raw_transcripts`;
- `transcript_segments`;
- `pseudonym_mappings`.

Это дополнительная защита на случай ошибочного будущего GRANT. Она не заменяет отдельные schemas/Credentials.

## Capability roles

Создано 9 NOLOGIN ролей:

1. `shablon_analiz_telefonnyh_peregovorov_orchestrator`;
2. `shablon_analiz_telefonnyh_peregovorov_core`;
3. `shablon_analiz_telefonnyh_peregovorov_privacy`;
4. `shablon_analiz_telefonnyh_peregovorov_raw_transcript_reader`;
5. `shablon_analiz_telefonnyh_peregovorov_knowledge_reader`;
6. `shablon_analiz_telefonnyh_peregovorov_knowledge_admin`;
7. `shablon_analiz_telefonnyh_peregovorov_dashboard`;
8. `shablon_analiz_telefonnyh_peregovorov_admin_api`;
9. `shablon_analiz_telefonnyh_peregovorov_monitor`.

Все роли:

- NOLOGIN;
- NOSUPERUSER;
- NOCREATEDB;
- NOCREATEROLE;
- NOINHERIT;
- NOREPLICATION;
- NOBYPASSRLS.

### Orchestrator

Разрешено:

- managers/calls/events;
- operations/attempts;
- filter decisions;
- call links;
- temporary audio metadata;
- safe pseudonymized pipeline outputs;
- CRM confirmations;
- callback/outgoing/delivery state;
- active filter rules.

Запрещено:

- raw transcript;
- raw segment;
- reverse mapping;
- knowledge publication/edit;
- audit mutation;
- schema CREATE.

### CORE

Разрешено:

- safe pseudonymized inputs;
- privacy package;
- quality/speech metrics;
- только active+passed prompt/methodology views;
- только published product-scoped knowledge;
- analysis/evidence create/update;
- необходимые evidence-gate calculation functions.

Запрещено:

- raw transcript/segments;
- pseudonym mapping;
- draft/base knowledge;
- knowledge publication/edit.

### Privacy

Единственная обычная processing-role с записью в:

- raw transcripts;
- transcript segments;
- role assignments;
- pseudonymized artifacts;
- privacy packages;
- reverse mapping;
- processing/speech quality.

RLS policy разрешает этой роли raw/mapping access.

### Raw transcript reader

Отдельная capability `view_raw_transcript`.

Разрешено только read raw transcript/segments.

Не разрешено:

- mapping;
- UPDATE;
- dashboard/admin/knowledge права.

Это позволяет включать raw-view только для отдельно разрешённого backend endpoint.

### Knowledge reader

Разрешён только:

`v_runtime_knowledge_call_analysis`.

Он не читает base/draft knowledge tables и не может publish/edit.

### Knowledge admin

Отдельная привилегированная shablon_analiz_telefonnyh_peregovorov capability:

- prompt/methodology/filter configs;
- knowledge documents/versions/fragments/embeddings;
- publication manifest/membership;
- safe audit read + audit insert.

Она не имеет call/raw/mapping доступа и не должна использоваться как runtime analysis Credential.

### Dashboard

Read-only capability.

Разрешены:

- DB-06 metric views/functions;
- safe analysis provenance;
- privacy-passed pseudonymized segments;
- safe conversation evidence;
- safe absence evidence;
- exact used knowledge evidence;
- safe correction/dispute/feedback views.

Dashboard **не** получает direct SELECT на:

- raw transcripts;
- transcript segments;
- pseudonym mappings;
- base pseudonymized/evidence tables после hardening;
- base knowledge tables.

И не получает direct business-table writes.

### Admin API

Получает safe dashboard/admin views и две controlled SECURITY DEFINER functions:

- `admin_submit_analysis_dispute`;
- `admin_propose_correction`.

Функции создают только request/proposal + immutable audit event.

Они **не** применяют correction автоматически и не переписывают analysis. Финальное downstream correction/reanalysis остаётся отдельной будущей operation.

### Monitor

Разрешены только content-minimized views:

- `v_monitor_operations`;
- `v_monitor_audio_cleanup`;
- `v_monitor_delivery`.

Transcript/message/recipient/knowledge content в monitoring surfaces не входит.

## Runtime active-only views

Созданы security-barrier views:

- `v_runtime_prompt_active`;
- `v_runtime_methodology_active`;
- `v_runtime_methodology_criteria_active`;
- `v_runtime_methodology_stages_active`;
- `v_runtime_filter_rules_active`;
- `v_runtime_knowledge_call_analysis`.

CORE/runtime не читает draft/unvalidated configuration напрямую.

Knowledge view дополнительно фиксирован на:

`product_code = 'call_analysis'`.

## Dashboard safe views

Созданы:

- `v_dashboard_analysis_provenance`;
- `v_dashboard_safe_transcript_segments`;
- `v_dashboard_evidence_conversation`;
- `v_dashboard_evidence_absence`;
- `v_dashboard_knowledge_evidence`;
- `v_dashboard_corrections_safe`;
- `v_dashboard_disputes_safe`;
- `v_dashboard_feedback_safe`;
- `v_admin_audit_safe`.

### Privacy-safe transcript

`v_dashboard_safe_transcript_segments` включает segment только если:

- он входит в exact privacy package membership;
- package имеет `privacy_status='passed'`;
- package не invalidated.

Поэтому dashboard не получает blocked/candidate raw-like path через прямой base-table SELECT.

### Conversation evidence

Связывает evidence только с privacy-passed safe segment.

### Absence evidence

Показывает scope/coverage/result/rule из `evidence_absence_checks`, но не raw text.

### Knowledge evidence

Показывает fragment text только когда fragment был exact input/evidence конкретного analysis.

Исправлен найденный дефект ранней версии: используется реальная колонка `knowledge_ref_id`, а не несуществующая `evidence_knowledge_ref_id`.

## RLS policies

Создано 5 policies:

- `raw_transcripts_privacy_all`;
- `raw_transcripts_reader_select`;
- `transcript_segments_privacy_all`;
- `transcript_segments_reader_select`;
- `pseudonym_mappings_privacy_all`.

Смысл:

- privacy role может работать с raw/mapping;
- raw reader может только читать raw transcript/segments;
- raw reader не видит reverse mapping;
- другие runtime roles не получают policy path.

## PUBLIC/default privilege hardening

Migration выполняет:

- REVOKE ALL ON SCHEMA FROM PUBLIC;
- REVOKE ALL ON ALL TABLES FROM PUBLIC;
- REVOKE ALL ON ALL SEQUENCES FROM PUBLIC;
- REVOKE EXECUTE ON ALL FUNCTIONS FROM PUBLIC.

Также default privileges владельца migration настроены так, чтобы будущие tables/sequences/functions не получили ambient PUBLIC access, особенно PUBLIC EXECUTE на новых функциях.

## Verification

`007_access_isolation_verify.sql` запускается в транзакции и делает ROLLBACK.

Он создаёт временные probe schemas:

- другой shablon_analiz_telefonnyh_peregovorov contour;
- production-like contour.

После rollback они не остаются.

Verify проверяет:

- наличие и безопасные attributes всех 9 roles;
- отсутствие member/login bindings до DB-08B;
- USAGE своего schema и отсутствие CREATE;
- отсутствие доступа к другому test/prod probe;
- RLS на 3 sensitive tables;
- 5 нужных policies;
- positive/negative privilege matrix каждой capability;
- raw-reader отдельно от mapping;
- knowledge reader только product-scoped published view;
- knowledge admin отдельно от call/privacy data;
- active+passed runtime configs;
- dashboard только safe views;
- SECURITY DEFINER admin functions и pinned search_path;
- отсутствие PUBLIC relation privileges;
- отсутствие PUBLIC EXECUTE на всех shablon_analiz_telefonnyh_peregovorov functions;
- отсутствие default PUBLIC EXECUTE для будущих функций;
- отсутствие DELETE/TRUNCATE у capability roles;
- `security_barrier=true` на DB-07 views;
- отсутствие business columns с именами password/token/secret/credential;
- отсутствие broad admin attributes.

## Rollback

`007_access_isolation_rollback.sql`:

- проверяет roles/views/policies/functions;
- отказывается, если capability role уже выдана реальному member/login role;
- отказывается при later/unknown relations;
- удаляет RLS policies;
- отключает DB-07 RLS на 3 sensitive tables;
- удаляет 2 admin functions;
- удаляет 18 DB-07 views;
- снимает grants;
- восстанавливает pre-DB-07 PUBLIC EXECUTE функций;
- восстанавливает соответствующий default function privilege;
- удаляет 9 NOLOGIN roles.

CASCADE не используется.

## Статическая проверка

Подтверждено по GitHub:

- migration: 9 roles / 18 views / 2 SECURITY DEFINER functions / 5 policies;
- rollback содержит тот же набор roles/views/functions/policies;
- SQL lexical structure сбалансирована;
- duplicate DB-07 file set удалён;
- plaintext password отсутствует;
- `service_role` не используется;
- `bytea/blob` отсутствуют;
- production schema DDL отсутствует;
- CASCADE отсутствует;
- признаки типовых реальных секретов не найдены;
- все 18 DB-07 views проверены по порядку зависимостей: нет ссылок на ещё не созданные relations;
- обе SECURITY DEFINER functions ссылаются только на уже существующие DB-05 objects/types и имеют фиксированный `search_path`;
- 9 role identifiers имеют длину не более 59 символов и помещаются в PostgreSQL identifier limit;
- migration не создаёт LOGIN identities и не назначает capability-role memberships.

Поэтому нельзя утверждать:

- roles/policies/grants применены;
- RLS реально блокирует/разрешает ожидаемые запросы;
- verify реально PASS;
- CREATE ROLE разрешён working Supabase identity;
- реальные working LOGIN Credentials разделены;
- API/dashboard/n8n используют правильные Credentials;
- production isolation готова.
