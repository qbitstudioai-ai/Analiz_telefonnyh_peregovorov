# DB-05 — CRM-факты, доставка, исправления и аудит

Статус: migration **фактически применена к рабочему Supabase**, verify DB-05 ещё не выполнен.

Зависимости: DB-01—DB-04.

## Цель

Создать физический слой для:

- подтверждённых CRM/человеком бизнес-фактов;
- связей пропущенного звонка и callback;
- исходящих действий до внешней отправки;
- истории delivery attempts;
- безопасного `outcome_unknown` и reconciliation;
- disputes;
- corrections;
- append-only audit trail.

DB-05 не реализует права/RLS — это DB-07. Не выполняет реальную отправку и CRM sync — это будущие n8n/CORE задачи.

## Файлы

- `supabase/migrations/005_crm_outgoing_corrections_audit.sql`;
- `supabase/verify/005_crm_outgoing_corrections_audit_verify.sql`;
- `supabase/rollback/005_crm_outgoing_corrections_audit_rollback.sql`.

## Физические сущности

Migration создаёт 7 таблиц:

1. `business_confirmations`;
2. `callback_links`;
3. `outgoing_actions`;
4. `delivery_attempts`;
5. `analysis_disputes`;
6. `corrections`;
7. `audit_events`.

Также создаются 10 enum-типов, 15 функций и 18 triggers.

## CRM/human confirmations

`business_confirmations` физически отделена от `ai_inferred_outcomes`.

Подтверждение хранит:

- call;
- fact family;
- тип факта;
- CRM/human source;
- source system/event key;
- external fact ID при наличии;
- client/deal refs;
- value/status;
- время бизнес-факта;
- время получения;
- human actor при ручном подтверждении;
- operation provenance.

Первый event семейства обязан быть `confirm`.

Исправление/отмена создаются отдельными `correct/cancel` events:

- predecessor обязателен;
- event_no идёт строго по цепочке;
- call и fact type не меняются;
- predecessor не может иметь две параллельные successor-ветки;
- прошлый event не обновляется и не удаляется.

Таким образом CRM payment или human confirmation не превращает AI outcome в тот же объект.

## Callback links

`callback_links` связывает два разных звонка:

- исходный missed call;
- последующий outbound callback;
- manager при наличии;
- trusted basis refs;
- rules/window config;
- delay;
- candidate/confirmed/rejected decision.

Confirmed link требует непустое доверенное основание.

Callback не может происходить раньше missed call.

После финального confirmed/rejected решение и его basis immutable; delete истории блокируется.

## Outgoing action

`outgoing_actions` создаётся **до внешнего send** и фиксирует:

- exact call;
- exact validated/current analysis;
- logical action key;
- purpose;
- server-selected channel;
- trusted recipient ref;
- message version/body/hash;
- creation operation.

Action всегда вставляется как `prepared`.

Creation operation должна быть `succeeded`.

Содержимое, адресат, channel и pinned analysis после создания не меняются. Допустим только контролируемый переход в `cancelled`.

Новый current analysis сам по себе не создаёт новый outgoing action.

## Delivery attempts

Каждая реальная попытка доставки — отдельная строка `delivery_attempts`.

Она физически ссылается на:

- существующий outgoing action;
- exact operation;
- exact operation attempt;
- provider request ID;
- transport result;
- provider-confirmed status;
- operation outcome;
- retry safety;
- reconciliation state.

### Confirmed delivery

`succeeded` допускается только если:

- provider status = `delivered`;
- transport = `transport_succeeded`;
- есть delivered timestamp;
- retry запрещён.

После delivered/confirmed_delivered новый attempt того же outgoing action блокируется.

### failed_retryable

`safe_retry_allowed=true` физически допустим только вместе с `failed_retryable`.

Для `succeeded`, `failed_requires_fix` и `outcome_unknown` safe retry = false.

### outcome_unknown

При `outcome_unknown`:

- provider status остаётся unknown/not_confirmed/accepted;
- automatic safe retry запрещён;
- reconciliation state обязан быть `pending`.

Пока reconciliation = pending/unresolved, новый send attempt блокируется.

Reconciliation может завершить старую попытку только как:

- `confirmed_delivered`;
- `confirmed_not_delivered`;
- `unresolved`.

Для reconciliation требуется отдельная succeeded operation.

Только `confirmed_not_delivered` снимает неизвестность так, что последующая новая попытка не блокируется прежним unknown.

Оригинальные transport/provider/outcome facts при reconciliation не переписываются.

## Disputes

`analysis_disputes` — запрос на проверку, а не прямое изменение score.

Dispute:

- обязан начинаться как `open`;
- может ссылаться на exact analysis, claim и evidence;
- сохраняет автора и причину;
- target/author/reason immutable;
- после resolved/rejected запись immutable;
- delete блокируется.

## Corrections

`corrections` хранит controlled correction metadata.

Ровно один typed target:

- manager;
- role assignment;
- transcript;
- analysis;
- business confirmation;
- callback link;
- outgoing action.

Correction хранит:

- before/after refs;
- before/after safe JSON;
- actor;
- reason;
- optional source dispute;
- apply operation.

Новая correction обязана быть `proposed`.

Прямой INSERT как applied/rejected запрещён.

Применение требует отдельной succeeded operation.

Applied/rejected correction immutable и не стирает исходный объект.

Сам downstream-version/reanalysis создаётся профильным процессом; correction row не переписывает versioned source in-place.

## Audit trail

`audit_events` — append-only технический/административный журнал.

Хранит:

- test scope/environment;
- actor;
- capability;
- action type;
- target type/ref;
- before/after refs;
- reason;
- operation;
- success/rejected/unknown result;
- error code;
- source channel;
- safe details;
- request/result timestamps.

Audit event нельзя UPDATE или DELETE обычной операцией.

Результат имеет обязательное `result_at`.

Plaintext secrets не являются частью audit schema.

## Verification

`005_crm_outgoing_corrections_audit_verify.sql` выполняется в транзакции и завершает её `ROLLBACK`.

Он проверяет:

- наличие 7 tables;
- наличие 10 enum types;
- наличие 15 functions;
- наличие 18 triggers;
- exact operation-attempt key;
- exact role/call key;
- отсутствие AI refs в trusted business confirmation;
- outgoing action exact analysis/call FK;
- delivery attempt требует уже существующий outgoing action;
- delivery связан с exact operation attempt;
- safe retry semantics;
- succeeded означает provider-confirmed delivered;
- callback candidate/final decision metadata;
- audit result time;
- наличие guard против repeated delivered attempt;
- наличие reconciliation gate для outcome_unknown;
- typed correction target;
- запрет direct resolved dispute INSERT;
- запрет direct applied correction INSERT;
- запрет direct cancelled outgoing INSERT;
- реальную append-only защиту audit UPDATE/DELETE на test row.

Полный happy-path с реальными upstream fixture rows будет фактически проверен при DB-08B после применения всей migration chain в рабочей schema `shablon_analiz_telefonnyh_peregovorov` PostgreSQL/Supabase.

## Rollback

`005_crm_outgoing_corrections_audit_rollback.sql`:

- оставляет DB-01—DB-04;
- удаляет ровно 7 DB-05 tables;
- удаляет 15 DB-05 functions;
- удаляет 10 DB-05 enum types;
- снимает две composite unique constraints, добавленные DB-05 к upstream tables;
- не использует CASCADE;
- отказывается запускаться при неполном DB-05;
- отказывается запускаться при later/unknown relations.

После DB-06+ DB-05 rollback нельзя выполнять отдельно без отката зависимой цепочки.
