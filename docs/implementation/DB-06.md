# DB-06 — dashboard views и metric SQL

Статус: SQL создан и усиленно статически проверен; **следующая migration для фактического применения в DB-08B**.

Зависимости: DB-01—DB-05.

## Цель

Создать единый server-side слой данных дашборда, который реализует [METRICS](../specs/METRICS.md) и [DASHBOARD_DATA_MAP](../DASHBOARD_DATA_MAP.md) без альтернативных формул в браузере или n8n.

DB-06 не реализует UI и права доступа. Изоляция views/functions и runtime roles относятся к DB-07.

## Файлы

- `supabase/migrations/006_dashboard_metrics.sql`;
- `supabase/verify/006_dashboard_metrics_verify.sql`;
- `supabase/rollback/006_dashboard_metrics_rollback.sql`.

## Общий принцип

Главная строка дашборда — **один логический `call_id`**, а не webhook/event/attempt.

Повторный webhook находится в `call_events` и поэтому физически не увеличивает call metrics второй раз.

Все страницы дашборда используют один фильтрующий контракт:

`dashboard_filter_call_ids(start, end, filters)`.

Период:

- start включительно;
- end не включительно;
- сервер заранее переводит локальный период компании в `timestamptz`.

Поддерживаются общие фильтры:

- manager;
- department;
- source;
- direction;
- first/repeat;
- reliability;
- classification;
- terminal category;
- AI outcome type;
- CRM fact type.

## Views

Создано 12 views.

### Helper views

1. `v_dashboard_business_confirmations_current`
   - выбирает последний immutable CRM/human event каждого fact family;
   - cancelled family не входит в current metrics;
   - история не удаляется.

2. `v_dashboard_delivery_current`
   - одна текущая delivery-state строка на outgoing action;
   - различает pending, delivered, unknown, not_delivered, retryable, requires-fix, cancelled.

3. `v_dashboard_processing_quality_current`
   - последняя current processing quality на call.

4. `v_dashboard_speech_metrics_current`
   - последняя current speech-metric version на call.

### Основные views

5. `v_dashboard_zvonki`
   - одна строка на logical call;
   - manager/source/direction/first-repeat;
   - current filter decision;
   - exact current analysis/version refs;
   - AI outcome и CRM fact массивы раздельно;
   - callback;
   - latest feedback delivery;
   - terminal metric category;
   - official score.

6. `v_dashboard_obshchaya_kartina`
   - четыре взаимоисключающие terminal categories;
   - reliable/preliminary/technically incomplete flags;
   - first/repeat;
   - callback flags.

7. `v_dashboard_menedzhery`
   - one-call metric rows с manager dimensions;
   - aggregate рассчитывается общей функцией после одинаковых фильтров.

8. `v_dashboard_kriterii`
   - current analysis criterion rows;
   - applicability;
   - score/weight;
   - evidence ID;
   - dispute flag.

9. `v_dashboard_etapy`
   - applicable/reached/required stage;
   - last reached stage;
   - evidence ID;
   - dispute flag.

10. `v_dashboard_oshibki`
    - stable observation code/type;
    - criterion/stage context;
    - evidence ID;
    - dispute flag.

11. `v_dashboard_rezultaty`
    - единая reporting shape;
    - `result_source='ai'` отдельно;
    - trusted `crm/human` отдельно;
    - AI evidence ID не превращается в CRM evidence;
    - AI row имеет aggregate eligibility с учётом dispute.

12. `v_dashboard_kachestvo`
    - processing quality;
    - warning codes;
    - speech quality;
    - речевые показатели только при reliable speech metrics.

## Разложение звонков

`v_dashboard_zvonki.terminal_metric_category` имеет ровно четыре смысловые категории:

- `evaluated_client`;
- `excluded`;
- `missed_client`;
- `pending_or_technical`.

Каждый logical call получает одну категорию.

Приоритет:

1. окончательно excluded;
2. missed;
3. client с допустимым current analysis;
4. остальное — pending/technical.

Это позволяет проверять:

`all calls = evaluated + excluded + missed + pending/technical`.

First/repeat — дополнительный разрез client calls и не прибавляется к этой сумме.

## Current analysis и dispute

Dashboard использует только `analysis_state='current'`.

Открытый dispute (`open/under_review`) не скрывает analysis из карточки звонка, но исключает его из официальных агрегатов.

Так выполняется требование METRICS: disputed analysis не подменяется старым результатом и не продолжает влиять на официальный показатель.

## Official score

`official_score` существует только когда одновременно:

- call = client;
- есть current analysis;
- analysis reliability = reliable;
- нет open dispute.

`dashboard_overview` и `dashboard_manager_metrics` считают average только из этого поля.

Preliminary и technically incomplete анализы считаются отдельно.

## Criterion metrics

`dashboard_criterion_metrics`:

- использует только current reliable non-disputed analyses;
- берёт только `applicable=true`;
- N/A не становится zero;
- возвращает denominator count и exact `call_ids`.

## Stage metrics

`dashboard_stage_metrics`:

- использует reliable non-disputed analyses;
- denominator = calls, где stage applicable;
- reached = applicable + reached;
- missed required = applicable + required + not reached;
- возвращает exact call IDs для reached и missed.

Отсутствующее/неприменимое возражение не ухудшает stage percentage.

## Observation metrics

`dashboard_observation_metrics` группирует stable observation code вместе с его criterion/stage context.

Denominator определяется не наличием самой ошибки, а applicable context:

- если observation связана с criterion — reliable analyses, где criterion applicable;
- если связана со stage — reliable analyses, где stage applicable;
- если context отсутствует — все filtered reliable analyses.

Это предотвращает бессмысленную долю 100% от «строк, где ошибка уже встретилась».

Если один stable code используется в разных criterion/stage contexts, он остаётся различимым в SQL-результате до отдельного бизнес-решения объединять такие контексты.

## AI и CRM results

AI outcome и CRM/human confirmation:

- физически разные первичные сущности;
- в reporting view имеют явный `result_source`;
- агрегируются раздельно.

`dashboard_result_metrics` возвращает:

- source;
- result code;
- unique logical calls;
- exact drill-down call IDs.

Открытый dispute исключает AI outcome из официального result aggregate, но не удаляет его из call history.

CRM факт остаётся независимым от dispute AI-analysis.

## Target conversion

«Целевой код» является параметром компании, поэтому DB-06 его не выдумывает.

`dashboard_overview` и `dashboard_manager_metrics` принимают:

- `p_target_ai_outcome_codes text[]`;
- `p_target_crm_fact_types text[]`.

Если массив не передан, соответствующая target metric возвращается NULL, а не произвольное число.

AI conversion:

`target AI calls / evaluated client calls × 100%`.

CRM target count остаётся отдельной цифрой.

## Missed/callback

Confirmed callback считается только из `callback_links.link_state='confirmed'`.

Callback rate:

`missed with confirmed callback / all missed client calls × 100%`.

Для «без перезвона» нужен срок компании. Он передаётся как:

`p_callback_window interval`.

Call считается `without_callback_after_window` только если:

- он missed;
- confirmed callback отсутствует;
- `started_at + callback_window <= as_of`.

Свежий missed call до окончания окна не объявляется «без перезвона».

Число окна DB-06 не выдумывает.

## Speech metrics provenance

Если current analysis существует, speech metrics показываются только когда их:

- raw transcript;
- role assignment

совпадают с exact inputs current analysis.

Это запрещает показать новые speech metrics рядом со старым анализом после correction/reprocessing.

Само значение speech metric выводится только при `reliability='reliable'`.

## Drill-down

Metric functions возвращают exact `call_ids` для criteria/stages/observations/results, где это требуется.

Агрегат не получает искусственное «общее evidence».

Дальнейший переход call → claim/evidence использует DB-04 evidence IDs.

## Functions

Создано 7 функций:

1. `dashboard_filter_call_ids`;
2. `dashboard_overview`;
3. `dashboard_manager_metrics`;
4. `dashboard_criterion_metrics`;
5. `dashboard_stage_metrics`;
6. `dashboard_observation_metrics`;
7. `dashboard_result_metrics`.

Все агрегирующие функции используют один shared call filter.

## Verification

`006_dashboard_metrics_verify.sql` проверяет:

- наличие 12 views;
- наличие 7 functions;
- call dashboard основан на logical calls, а не webhook events;
- четыре terminal categories;
- dispute exclusion;
- AI/CRM source separation;
- latest non-cancelled CRM chain;
- speech reliability gate;
- единый period/filter contract;
- official average formula;
- N/A/reliable/dispute criterion gate;
- applicable stage denominator;
- observation applicability denominator;
- result source + drill-down;
- invalid period rejected;
- filters must be JSON object;
- negative callback window rejected.

Полноценные численные fixture cases будут фактически выполнены при DB-08B после применения DB-01—DB-07 в рабочей schema `shablon_analiz_telefonnyh_peregovorov` в Supabase.

## Rollback

`006_dashboard_metrics_rollback.sql`:

- оставляет DB-01—DB-05;
- удаляет 7 metric functions;
- удаляет 12 DB-06 views в обратном порядке зависимостей;
- не использует CASCADE;
- отказывается запускаться при неполном DB-06;
- отказывается запускаться при later/unknown relations.

Подтверждено:

- migration: 12 views / 7 functions;
- rollback: тот же набор views/functions;
- SQL lexical structure сбалансирована;
- CASCADE отсутствует;
