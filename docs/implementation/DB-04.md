# DB-04 — анализ и доказательства

Статус: SQL создан и статически проверен; **следующая migration для фактического применения в DB-08B**.

Зависимости: DB-01, DB-02, DB-03.

## Цель

Создать физическую модель для:

- immutable analysis versions;
- exact input manifest;
- criterion scores;
- call stages;
- observations;
- AI inferred outcomes;
- typed evidence targets;
- conversation evidence;
- knowledge evidence;
- absence evidence;
- evidence coverage/reference integrity;
- evidence gate перед current analysis.

DB-04 не реализует runtime roles/RLS — это DB-07. Не отправляет данные в LLM и не запускает reanalysis — это будущие CORE/n8n задачи.

## Файлы

- `supabase/migrations/004_analysis_evidence.sql`;
- `supabase/verify/004_analysis_evidence_verify.sql`;
- `supabase/rollback/004_analysis_evidence_rollback.sql`.

## Физические сущности

Migration создаёт 11 таблиц:

1. `analysis_versions`;
2. `analysis_knowledge_inputs`;
3. `analysis_claims`;
4. `criterion_scores`;
5. `stage_results`;
6. `analysis_observations`;
7. `ai_inferred_outcomes`;
8. `evidence_sets`;
9. `evidence_conversation_refs`;
10. `evidence_knowledge_refs`;
11. `evidence_absence_checks`.

Также создаются 9 enum-типов, 13 функций и 18 triggers.

## Immutable analysis input manifest

Одна строка `analysis_versions` фиксирует exact:

- call;
- analysis operation;
- raw transcript;
- role assignment version;
- pseudonymized transcript;
- privacy package;
- processing quality version;
- prompt version;
- methodology version;
- knowledge publication;
- model/provider/config;
- analysis contract;
- CORE/validator version;
- input manifest hash;
- LLM response hash.

Связи с transcript/roles/privacy/quality физически проверяются составными FK, чтобы нельзя было собрать analysis из несовместимых версий разных звонков или разных upstream chains.

## Analysis lifecycle

Состояния:

- `candidate`;
- `validated`;
- `current`;
- `superseded`;
- `invalidated`.

Новая analysis обязана создаваться только как `candidate`.

DB-04 отдельно блокирует:

- прямой INSERT сразу как `validated/current`;
- candidate INSERT с заранее объявленным passed evidence gate;
- возврат validated/current/history обратно в candidate;
- semantic mutation после validation.

Во время разработки DB-04 был найден и исправлен важный обход: первоначальная версия защищала только UPDATE-переход candidate → validated/current, но позволяла теоретически вставить final-state строку напрямую. Добавлен `guard_analysis_initial_state()` и regression-проверки в verify SQL.

## Exact knowledge inputs

`analysis_knowledge_inputs` хранит не всю publication, а exact fragments, реально доступные конкретному analysis.

Каждый fragment обязан одновременно:

- принадлежать pinned `knowledge_publication_id`;
- входить в publication membership;
- иметь explicit product scope `call_analysis`.

Evidence по знаниям может ссылаться только на этот exact set.

## Typed claims

`analysis_claims` является typed base target для:

- criterion score;
- stage result;
- observation;
- AI outcome.

Свободный строковый `target_ref` не используется.

Дочерние таблицы связаны с exact claim и exact analysis через FK.

## Criteria и stages

Criterion score физически связан с:

- exact analysis;
- exact methodology version;
- criterion code, существующим в этой methodology.

Stage result аналогично связан с exact methodology stage.

`not applicable` хранится отдельно от низкого/нулевого score.

Overall score рассчитывается функцией как weighted average только применимых criterion rows с положительным weight.

## Observations и AI outcome

Observation имеет stable code, тип `error/strength/warning` и может быть связан с exact criterion/stage текущей methodology.

AI inferred outcome остаётся отдельным объектом и не является CRM confirmation.

CRM-факты физически будут реализованы в DB-05.

## Evidence model

`evidence_sets` различает:

- evidence type: presence / absence_check / knowledge / composite;
- reference integrity: pending / verified / invalid / unavailable_by_retention;
- coverage: pending / complete / partial / not_applicable;
- rule kind: criterion / stage / analysis.

Reference integrity подтверждает корректность source refs, но не объявляет вывод LLM истинным.

## Conversation evidence

`evidence_conversation_refs` может ссылаться только на pseudonymized segment, который:

- входит в exact pinned privacy package;
- принадлежит analysis;
- имеет совпадающие time boundaries/business role.

Quote snapshot при наличии должен реально встречаться в exact pseudonymized segment.

Raw transcript segment нельзя подставить вместо разрешённого privacy package segment.

## Knowledge evidence

`evidence_knowledge_refs` имеет составной FK:

`(analysis_id, fragment_id) → analysis_knowledge_inputs`.

Поэтому knowledge fragment, который существует в БД/publication, но не был exact input конкретного analysis, не может стать evidence этого analysis.

Excerpt snapshot при наличии должен реально встречаться в exact fragment text.

## Absence evidence

Отсутствие действия не подтверждается выдуманной цитатой.

`evidence_absence_checks` хранит:

- whole conversation / stage / interval scope;
- exact privacy package;
- exact methodology;
- exact processing quality;
- coverage sufficiency;
- результат отсутствия;
- checked rule code.

Technically incomplete processing не может заявить достаточное coverage для absence check.

## Evidence gate

Перед переходом analysis в validated/current БД проверяет:

- CORE validation = passed;
- evidence gate status = passed;
- analysis operation succeeded;
- privacy package passed;
- pinned prompt/methodology были active или допустимо historical;
- pinned knowledge publication была published/historical-valid;
- analysis имеет structured claims;
- каждому typed claim соответствует typed child row;
- pending/invalid evidence отсутствует;
- каждый обязательный claim имеет complete verified evidence нужного типа;
- presence имеет conversation ref;
- knowledge имеет knowledge ref;
- absence_check имеет sufficient/absent check;
- composite имеет conversation + knowledge refs;
- overall score совпадает с расчётом criterion scores.

Analysis не может стать `current` напрямую из candidate: сначала требуется `validated`.

## Immutability

Child analysis rows можно менять только пока parent analysis = candidate.

После verification evidence semantics/refs freeze.

После lawful retention verified evidence может перейти в `unavailable_by_retention`, не перепривязываясь к новому source.

Historical analysis не переписывается после новой версии входов.

## Verification

`004_analysis_evidence_verify.sql` запускается в транзакции и завершает её `ROLLBACK`.

Он проверяет:

- наличие 11 DB-04 tables;
- наличие 9 enum types;
- наличие 13 DB-04 functions;
- наличие 18 DB-04 triggers;
- exact composite keys, добавленные к privacy/quality inputs;
- наличие обязательных input-manifest columns;
- product-scoped knowledge input FK;
- exact privacy-package segment FK;
- exact analysis knowledge-input FK;
- exact absence privacy-package FK;
- отсутствие free-form evidence refs;
- unique partial current-analysis index;
- подключение structural evidence gate к analysis transition;
- запрет прямого INSERT сразу как current;
- запрет candidate INSERT с заранее passed evidence gate.

DB-01—DB-03 имеют собственные fixture verification SQL; DB-04 verify не дублирует их сотнями строк upstream fixture data.

Фактический совместный PostgreSQL/Supabase run всей цепочки запланирован на DB-08B.

## Rollback

`004_analysis_evidence_rollback.sql`:

- оставляет DB-01—DB-03;
- удаляет ровно 11 DB-04 tables;
- удаляет 13 DB-04 functions;
- удаляет 9 DB-04 types;
- снимает только две composite unique constraints, добавленные DB-04 к DB-02 tables;
- не использует CASCADE;
- отказывается запускаться при неполном DB-04;
- отказывается запускаться, если появились later/unknown relations.

После DB-05+ rollback DB-04 нельзя выполнять отдельно без отката зависимой цепочки.

## Статическая проверка

Подтверждено по файлам GitHub:

- migration: 11 tables / 13 functions / 9 types / 18 triggers;
- rollback: наборы tables/functions/types совпадают с migration;
- SQL lexical structure сбалансирована;
- migration использует только `shablon_analiz_telefonnyh_peregovorov`;
- executable `service_role` отсутствует;
- `bytea/blob` отсутствуют;
- признаки типовых реальных секретов не найдены;
- initial-state bypass закрыт regression guard;
- fake/non-input knowledge/segment refs ограничены составными FK и gate logic.
