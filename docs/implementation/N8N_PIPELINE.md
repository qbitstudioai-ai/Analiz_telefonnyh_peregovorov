# N8N-00 — утверждённая логика pipeline n8n + WhisperX + Supabase

Статус: **логика согласована Павлом 27 сентября 2026 года**.

Это нормативное описание будущего общего n8n workflow до сборки JSON.

Важно различать статусы:

- логика pipeline — **согласована и записана в GitHub**;
- JSON workflow — **ещё не создан**;
- workflow в n8n — **ещё не импортирован**;
- Credentials — **ещё не подключены**;
- WhisperX через n8n — **ещё не вызван и не протестирован**;
- end-to-end обработка — **ещё не протестирована**;
- production traffic — **не подключён**.

## 1. Физическая архитектура

В обработке звонков нет отдельного CORE/backend.

Физическая связка:

- **n8n** — вся orchestration/business/safety-логика, Code-ноды, маршрутизация, retries и вызовы интеграций;
- **Supabase** — подтверждённое состояние, история, версии, права, знания, результаты и данные для метрик;
- **WhisperX** — локальный сервис транскрибации и диаризации, вызываемый n8n;
- **внешняя LLM** — получает только разрешённый псевдонимизированный пакет после privacy-gate;
- **CRM/телефония/оператор** — источники событий, метаданных и аудио;
- **Telegram/CRM/другой канал** — адаптер доставки мотивирующей обратной связи менеджеру;
- **dashboard** — отдельное приложение, читающее подготовленные Supabase views/functions.

Вся прикладная обработка аудиозаписи и результатов находится в n8n. Отдельный программный модуль обработки звонков не создаётся.

## 2. Главный принцип шаблона

При внедрении новой организации не должна переписываться основная последовательность pipeline.

Меняются только:

- входной адаптер источника;
- Credentials;
- правила фильтрации;
- внутренние/служебные номера;
- сотрудники/отделы;
- способ получения аудио;
- промт;
- методика и критерии;
- опубликованные знания;
- канал обратной связи;
- параметры retry/timeout/retention после фактических испытаний.

### Где живут настройки

**Supabase, версионируемые бизнес-настройки:**

- `filter_rule_versions`;
- `prompt_versions`;
- `methodology_versions`;
- `methodology_criteria`;
- `methodology_stages`;
- `knowledge_publications` и связанные knowledge tables.

**n8n Credentials / защищённые переменные:**

- токены CRM/телефонии;
- доступ к локальному WhisperX, если он требует auth;
- LLM API credentials;
- Telegram/CRM delivery credentials;
- Supabase runtime credential.

**Один понятный конфигурационный блок workflow «НАСТРОЙКИ КОМПАНИИ»:**

- тип входного адаптера;
- идентификатор подключения/аккаунта источника;
- технические URL локальных сервисов;
- channel type;
- product scope;
- non-secret adapter parameters.

Секреты, реальные номера и специфичные для одной компании правила не размазываются по Code-нодам.

## 3. Граница входного адаптера

Источник может быть:

- Bitrix24;
- другая CRM;
- виртуальная АТС;
- личный кабинет оператора связи;
- другой источник событий/записей.

Конкретные trigger/API-ноды могут отличаться, но адаптер обязан привести событие к одному внутреннему смыслу.

Минимально нормализуются:

- source type;
- source account/connection ref;
- external event ID;
- external call ID;
- направление;
- время начала/окончания;
- длительность, если известна;
- answered/missed;
- manager/source employee identifiers;
- номер второй стороны в доверенной внутренней ветке;
- CRM contact/lead/deal refs, если доступны;
- способ/URL получения аудио, если разрешён;
- дополнительные теги/отдел/metadata, разрешённые для фильтра.

Внешний payload не выбирает Supabase schema, runtime role или Credential.

## 4. Регистрация до дорогой обработки

Событие сначала надёжно фиксируется, и только потом запускаются дорогие этапы.

Основные Supabase сущности:

- `call_events` — факт входного события;
- `calls` — логический звонок;
- `operations` — логическая операция;
- `operation_attempts` — конкретная попытка;
- `managers` — доверенная связь менеджера;
- `call_links` — связи между звонками/сущностями, где применимо.

n8n сохраняет checkpoint перед следующим внешним/дорогим действием.

## 5. Contract / scope / idempotency checks

До обработки Code-ноды проверяют:

- поддерживаемую contract version;
- обязательные ID;
- разрешённый scope;
- соответствие input refs текущему контуру;
- отсутствие попытки внешнего payload переключить company/schema;
- идентичность logical operation;
- состояние предыдущей operation/attempt.

Решение нормализуется как:

- `accepted`;
- `duplicate`;
- `rejected`.

Повтор того же события не создаёт второй эквивалентный процесс.

Новое событие того же реального звонка не теряется как дубль: оно связывается с существующим `call_ref`, если это следует из доверенной идентичности источника.

Retry одной logical operation сохраняет `operation_id`, но получает новый `attempt_id`.

## 6. Ранняя фильтрация: до WhisperX

Ненужные разговоры отсекаются до получения/обработки аудио, если метаданных достаточно.

Фильтр компании может использовать комбинацию:

- white/black lists;
- внутренние и служебные номера;
- менеджера и отдел;
- направление звонка;
- CRM contact/lead/deal relation;
- теги CRM;
- тип линии/источника;
- длительность;
- другие доверенные metadata.

Номер телефона — важный признак, но не единственный источник истины.

Решение сохраняется в `filter_decisions`.

Минимальные категории:

- клиентский разговор — продолжить;
- личный/внутренний/служебный — исключить;
- пропущенный клиентский — отдельная ветка без WhisperX/LLM;
- неизвестная категория — допускается продолжить до транскрипции для второй классификации;
- rejected — прекратить из-за контракта/границы доступа.

Исключённый звонок сохраняется с причиной, но не получает оценку качества продаж.

## 7. Ветка пропущенного звонка

Если разговор не состоялся:

- аудио не ожидается;
- WhisperX не вызывается;
- LLM-анализ разговора не запускается;
- пропущенный звонок сохраняется как факт;
- позднее может связываться с подтверждённым callback через `callback_links`;
- окно callback является настройкой компании.

Неоднозначная связь не считается подтверждённым перезвоном.

## 8. Получение и временное хранение аудио

Только для принятого разговора n8n получает аудиофайл из выбранного source adapter.

Правила:

- бинарное аудио **не записывается в Supabase**;
- аудио существует только во временном локальном хранилище;
- Supabase хранит metadata и lifecycle временного файла в `temporary_audio_artifacts`;
- перед WhisperX фиксируется operation checkpoint;
- повтор получения аудио не должен создавать бесконтрольные копии;
- после завершения всех этапов, которым нужен звук, файл должен быть удалён;
- факт удаления фиксируется.

Конкретный максимальный retention будет параметром внедрения и не выдумывается шаблоном.

## 9. WhisperX

n8n передаёт локальный временный файл в WhisperX.

Ожидаемый смысл ответа:

- transcript;
- segments;
- start/end timestamps;
- technical speaker IDs;
- diarization;
- доступная model/config identity;
- доступные технические показатели качества.

n8n не доверяет ответу автоматически. Code-нода проверяет:

- что ответ относится к ожидаемым operation/attempt;
- обязательную структуру;
- диапазоны таймкодов;
- наличие/целостность сегментов;
- допустимость speaker refs;
- отсутствие структурной ошибки.

Невалидный ответ не становится подтверждённой транскрипцией.

## 10. Сохранение сырой транскрипции

После проверки результат WhisperX сохраняется в Supabase:

- `raw_transcripts` — версия исходной транскрипции и provenance;
- `transcript_segments` — сегменты/таймкоды/technical speaker;
- `processing_quality` — качество и надёжность обработки;
- `speech_metrics` — измеримые параметры речи, если качество позволяет.

Аудиофайл в эти таблицы не попадает.

## 11. Назначение ролей МЕНЕДЖЕР / КЛИЕНТ

Technical speaker из WhisperX не равен автоматически бизнес-роли.

n8n применяет согласованные доверенные признаки и сохраняет:

- `role_assignment_versions`;
- `role_assignments`.

Роль может быть:

- подтверждённой;
- предположенной;
- неопределённой.

Основание и качество назначения сохраняются. Низкая надёжность не скрывается.

## 12. Вторая фильтрация после транскрипции

Если до WhisperX категория была неизвестна или metadata недостаточны, n8n может выполнить вторую локальную классификацию по уже полученной транскрипции.

Цель — исключить, например:

- личный разговор;
- разговор с коллегой;
- разговор с монтажником/подрядчиком;
- другой не-клиентский разговор.

Полный дорогой LLM-анализ качества продаж после такого исключения не запускается.

Решение и причина остаются в Supabase.

## 13. Псевдонимизация и две логические ветки

После определения ролей n8n локально создаёт псевдонимизированную версию.

Supabase:

- `pseudonymized_transcripts`;
- `pseudonymized_segments`;
- `pseudonym_mappings`;
- `privacy_packages`;
- `privacy_package_segments`.

### Ветка A — аналитическая, без персональных данных

В LLM разрешено передавать только:

- псевдонимизированный текущий разговор;
- роли;
- безопасные segment refs;
- безопасный краткий контекст истории;
- промт;
- методику;
- разрешённые опубликованные знания;
- требуемую структуру ответа.

### Ветка B — доверенная внутренняя

Внутри n8n + Supabase остаются:

- реальные телефоны;
- реальные manager/contact/deal refs;
- pseudonym mapping;
- source identifiers;
- Credentials.

Эта ветка **не идёт в LLM**.

После ответа LLM результат связывается обратно с реальным звонком по внутренним доверенным refs. LLM не выбирает менеджера, телефон, получателя, schema или CRM deal.

## 14. Privacy-gate

Перед любым внешним LLM-вызовом n8n проверяет privacy package.

Если privacy status не PASS:

- внешний LLM вызов отсутствует;
- операция сохраняет машинно-различимое состояние/ошибку;
- дальнейшая аналитическая ветка блокируется.

Raw transcript, pseudonym mapping, аудио, secrets и реальные identifiers внешней LLM не отправляются.

## 15. Контекст истории и база знаний

Для принятого privacy package n8n загружает только разрешённые данные того же контура:

- current prompt version;
- current methodology version;
- applicable criteria/stages;
- active knowledge publication;
- точные разрешённые knowledge fragments через `v_runtime_knowledge_fragments`;
- краткий псевдонимизированный контекст прежних звонков, если доверенная связь с клиентом/сделкой существует.

В анализ фиксируются точные версии и exact fragment refs. Draft/unpublished/cross-company knowledge не используется.

## 16. Внешняя LLM

LLM получает обезличенный пакет и должна вернуть строго структурированный результат.

По смыслу ожидаются:

- оценки критериев;
- этапы разговора;
- сильные стороны;
- ошибки/наблюдения;
- рекомендации;
- предполагаемый результат разговора;
- evidence refs на переданные segment/knowledge refs;
- текст мотивирующей обратной связи менеджеру или структурные данные для её формирования;
- ограничения/предупреждения при низком качестве.

Обратная связь должна быть обучающей и мотивирующей, а не ругательной.

## 17. Проверка ответа LLM в n8n

Ответ LLM не записывается как подтверждённый анализ без Code-node validation.

Проверяются:

- формат;
- обязательные поля;
- допустимые criterion/stage/result codes;
- диапазоны score;
- отсутствие запрещённых PII/управляющих команд;
- evidence refs только на реально переданные segment/knowledge refs;
- согласованность с current methodology;
- наличие обязательных предупреждений при preliminary/low-quality analysis.

LLM не может своим текстом:

- переключить scope;
- назначить подтверждённую продажу;
- выбрать адресата сообщения;
- изменить Credential;
- выдать несуществующую цитату за evidence.

## 18. Сохранение анализа и доказательств

Только после validation n8n сохраняет согласованный набор фактов.

Основные Supabase сущности:

- `analysis_versions`;
- `analysis_knowledge_inputs`;
- `analysis_claims`;
- `criterion_scores`;
- `stage_results`;
- `analysis_observations`;
- `ai_inferred_outcomes`;
- `evidence_sets`;
- `evidence_conversation_refs`;
- `evidence_knowledge_refs`;
- `evidence_absence_checks`.

Сначала сохраняется подтверждённый анализ, затем допускается внешняя доставка обратной связи.

ИИ-результат остаётся отдельно от подтверждённого CRM/человеком бизнес-факта.

## 19. Метрики

n8n сохраняет первичные факты и результаты, необходимые для расчётов.

n8n **не создаёт собственные альтернативные формулы дашборда**.

Согласованные показатели рассчитываются уже созданными DB-06 views/functions:

- `v_dashboard_*`;
- `dashboard_overview`;
- `dashboard_manager_metrics`;
- `dashboard_criterion_metrics`;
- `dashboard_stage_metrics`;
- `dashboard_observation_metrics`;
- `dashboard_result_metrics`.

Так карточка, drill-down и выгрузка используют один источник определения метрики.

## 20. Быстрая мотивирующая обратная связь менеджеру

После сохранения анализа n8n без ожидания действий dashboard создаёт исходящее действие.

Обратная связь по смыслу содержит:

- что сделано хорошо;
- 1–3 главных точки улучшения;
- конкретную лучшую формулировку/приём;
- рекомендацию для следующего контакта, если он уместен;
- предупреждение о низкой надёжности анализа, если требуется.

Целевой принцип — максимально быстро после того, как аудио стало доступно и анализ подтверждён. Конкретный SLA определяется только после измерений WhisperX/LLM/source.

Канал является настройкой компании:

- Telegram;
- Bitrix24/CRM;
- другой разрешённый adapter.

## 21. Безопасная доставка

Перед внешней отправкой обязательно создаётся `outgoing_actions`.

После этого создаётся/фиксируется `delivery_attempts` и выполняется внешний вызов.

Правила:

- confirmed delivery не повторяется;
- duplicate event не создаёт вторую эквивалентную обратную связь;
- если внешний эффект мог произойти, но ответ потерян — `outcome_unknown`;
- при `outcome_unknown` слепая повторная отправка запрещена до reconciliation;
- auth/config error не превращается в бесконечный retry.

Фактический CRM результат сохраняется отдельно в `business_confirmations` и не переписывает ИИ-вывод.

## 22. Cleanup аудио

Когда больше нет разрешённого этапа, которому нужен звук:

- n8n удаляет временный аудиофайл;
- обновляет `temporary_audio_artifacts`;
- фиксирует факт/время удаления;
- ошибка cleanup остаётся наблюдаемой и подлежит recovery.

Удаление аудио не удаляет автоматически разрешённые transcript/analysis факты.

## 23. Ошибки, checkpoints и recovery

Значимое состояние не должно существовать только внутри памяти исполнения n8n.

Перед внешним/дорогим шагом нужный checkpoint уже сохранён в Supabase.

Минимально различаются:

- `not_started`;
- `in_progress_unconfirmed`;
- `succeeded`;
- `failed_retryable`;
- `failed_requires_fix`;
- `outcome_unknown`.

После restart n8n обработка восстанавливается из Supabase state.

Retry допустим только когда:

- нет подтверждённого succeeded;
- повтор безопасен;
- input versions всё ещё согласованы;
- нет параллельной попытки;
- состояние допускает retry.

## 24. Порядок end-to-end

Нормативный путь:

`Источник`
→ `нормализация события`
→ `регистрация Supabase`
→ `contract/scope/idempotency checks`
→ `ранняя фильтрация`
→ `пропущенный / исключённый: завершение своей ветки`
→ `получение временного аудио`
→ `WhisperX`
→ `валидация WhisperX`
→ `raw transcript + segments + quality в Supabase`
→ `назначение ролей`
→ `вторая фильтрация при необходимости`
→ `псевдонимизация`
→ `privacy-gate`
→ `prompt + methodology + knowledge + safe history`
→ `LLM`
→ `валидация LLM`
→ `analysis + evidence в Supabase`
→ `outgoing_action`
→ `Telegram/CRM delivery`
→ `delivery confirmation/reconciliation`
→ `cleanup audio`.

Dashboard независимо читает сохранённые Supabase views/functions и не ждёт доставки менеджеру.

## 25. Цель следующего JSON

Следующий этап — **N8N-JSON-01**.

ChatGPT должен собрать один полный импортируемый JSON первой версии общего pipeline, логически разделённый на понятные блоки/ноды.

В JSON:

- основные ноды имеют понятные русские названия;
- все Code-ноды содержат полный код;
- нет токенов/паролей;
- Credentials и значения, которые Павел заполняет после импорта, перечислены отдельно;
- source/channel-specific части изолированы как адаптерные зоны;
- настройки компании сосредоточены в одном блоке;
- workflow использует существующую schema `shablon_analiz_telefonnyh_peregovorov`;
- JSON не считается рабочим до фактического импорта и теста Павлом.

## 26. Что сознательно остаётся параметром внедрения

До фактического теста не выдумываются:

- конкретный API источника первой компании;
- конкретные Credentials;
- URL/способ auth WhisperX;
- модель/провайдер LLM;
- timeout/retry числа;
- максимальный audio retention;
- точный SLA обратной связи;
- конкретные black/white lists;
- конкретные filter rules;
- конкретный Telegram/CRM recipient mapping.

Эти значения заполняются/утверждаются при внедрении, не меняя общую логику pipeline.
