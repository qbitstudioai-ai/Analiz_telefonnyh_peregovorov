# Версионирование артефактов и анализа

Статус: DOC-13. Документ определяет, когда создаётся новая версия данных/настроек, как фиксируется точная комбинация входов анализа, как выбирается текущая действующая версия и что происходит при изменении зависимостей.

Это не SQL, не механизм sequence/UUID, не миграция и не команда на массовый перерасчёт исторических звонков.

## Цель

Для любого сохранённого анализа должно быть возможно ответить:

- какую версию транскрипции использовали;
- какое назначение ролей использовали;
- какой privacy-пакет реально разрешил внешний вызов;
- какой промт и методика действовали;
- какая модель/конфигурация фактически использована;
- какая публикация знаний и какие фрагменты были переданы;
- какой контракт ответа ожидался;
- какая версия CORE/валидатора влияла на проверку, если она меняет результат;
- какой результат был текущим в конкретный момент;
- почему прежний результат перестал быть текущим;
- требуется ли перерасчёт после изменения одного из входов.

Старая версия не должна менять смысл задним числом из-за того, что сегодня активна новая конфигурация.

## Основные понятия

### Версионное семейство

Версии сравниваются не глобально, а внутри одного логического семейства.

Примеры:

- исходные транскрипции одного call_ref;
- назначения ролей для конкретной версии транскрипции;
- промты одного профиля анализа;
- методики одного профиля/типа звонка;
- публикации знаний компании/среды;
- анализы одного звонка и одной цели анализа.

Версия из другого семейства не является «следующей» только потому, что создана позже.

### version_id

Каждая подтверждённая версия получает неизменяемый внутренний version_id.

version_id — источник точной ссылки. Человеческий номер вида v1/v2 может использоваться для отображения, но не заменяет стабильный ID.

### Предыдущая версия

Новая версия по возможности хранит связь с версией, от которой она произошла, и машинно/человеко-читаемую причину изменения.

Нельзя восстанавливать происхождение только по created_at.

### Текущая версия

current — это выбранная версия для конкретного семейства/контекста, а не свойство «самая новая строка по времени».

Текущая версия должна выбираться явным правилом/ссылкой.

Одновременно в одном семействе не должно быть двух current, если бизнес-смысл не предусматривает несколько параллельных профилей.

### Историческая версия

Версия, которая больше не current, остаётся исторической и сохраняет свои исходные ссылки.

Историческая не означает ошибочная.

### Invalidated

Если обнаружено, что версия была некорректной, повреждённой, нарушала privacy или иным образом не должна использоваться как действующая, это отдельное состояние/основание invalidated.

Invalidated не равно обычному superseded.

### Superseded

Версия superseded, когда её корректно заменила другая версия в том же семействе.

Она остаётся воспроизводимой исторической версией и продолжает объяснять старые результаты.

## Общий минимальный паспорт версии

Для версионируемой сущности должен быть доступен по смыслу:

- version_id;
- family_ref;
- predecessor_version_id, если есть;
- created_at;
- created_by_operation или доверенный автор;
- change_reason;
- состояние версии;
- ссылка на фактические входы;
- текущесть/историчность;
- superseded_by, если применимо;
- invalidation_reason, если версия признана недопустимой;
- доступность содержимого с учётом retention.

Физические поля и таблицы выбираются при реализации.

## Иммутабельность подтверждённой версии

После того как версия:

- использована downstream-операцией;
- опубликована;
- стала current;
- либо была основанием подтверждённого результата,

её смысловое содержимое не редактируется in place.

Исправление создаёт новую версию или отдельное корректирующее событие по правилам сущности.

Допустимо изменять техническую metadata, не меняющую смысл версии, например факт удаления содержимого по retention, но это не должно переписывать исторический контент задним числом.

## Одинаковый текст не всегда означает ту же версию

Версия определяется не только content.

Новая версия нужна, если изменилось происхождение или значимый способ получения результата, даже когда итоговый текст случайно совпал.

Пример: одна и та же транскрипция получилась после запуска другой модели. Это другой provenance и может быть отдельной версией.

Обратно: безопасный retry той же operation с теми же input_refs не должен создавать новую версию только из-за нового attempt_id.

## Два класса изменений

### Перспективное изменение

Меняет правило для будущих операций:

- новый промт;
- новая методика;
- новый model/config;
- новая публикация знаний;
- новая версия фильтра;
- новая версия алгоритма/CORE.

По умолчанию:

- будущие новые операции используют активную новую версию;
- уже подтверждённые старые анализы не переписываются;
- история массово не пересчитывается автоматически;
- старый анализ продолжает ссылаться на старую комбинацию версий.

Перерасчёт истории требует отдельной явной задачи/политики.

### Исправляющее изменение

Исправляет ошибочный или неполный вход конкретного звонка:

- ручная/проверенная коррекция транскрипции;
- исправление роли speaker;
- исправление privacy-пакета;
- обнаруженный критический дефект анализа/доказательства;
- исправление доверенной связи звонка, если она влияет на контекст анализа.

В этом случае зависимые результаты, основанные на исправленном входе, должны быть помечены как устаревшие/недействующие относительно текущего исправленного входа и не могут молча считаться официальным current.

Запускается новая downstream-цепочка там, где изменение действительно влияет на результат.

## Заморозка входов операции

Когда логическая операция анализа начинается, её набор input_refs фиксируется.

Изменение «текущего» промта, методики или знаний во время уже начавшейся операции не меняет её входы.

Retry той же operation_id использует тот же логический набор входов.

Если требуется использовать новую значимую версию входа, это новая логическая operation_id и новая целевая версия результата, а не retry старой операции.

## Analysis input manifest

Каждый анализ обязан иметь воспроизводимый manifest фактически использованных входов.

Минимально он включает:

- call_ref;
- исходную transcript version;
- role-assignment version;
- pseudonymized transcript version;
- privacy package version;
- prompt version;
- methodology version;
- model/provider/config identity;
- knowledge publication version;
- exact knowledge fragment refs, реально включённые в контекст;
- history context/package ref, если использовался;
- analysis contract_version;
- версию CORE/validator/postprocessing, если она может менять сохраняемый результат;
- quality-rules version, если она определяет nadezhno/predvaritelno;
- operation_id успешного анализа.

Manifest после подтверждения анализа неизменяем.

## Версия исходной транскрипции

Новая ishodnaya transkripciya version создаётся, когда меняется хотя бы один значимый фактор:

- используется другая версия/идентичность аудио;
- меняется движок/модель транскрибации;
- меняются параметры, способные изменить текст/таймкоды/technical speaker;
- получен новый подтверждённый результат после осознанного перерасчёта;
- человек или разрешённый процесс исправил текст/сегментацию;
- выявлена ошибка, требующая исправленной версии.

Не создаётся новая версия только потому, что:

- повторно доставлен тот же webhook;
- произошёл retry неуспешной attempt до появления первого подтверждённого результата;
- запись прочитали ещё раз без изменения подтверждённого артефакта и результата.

Версия хранит provenance движка/модели/конфигурации.

## Версия назначения ролей

Новая role-assignment version нужна, если:

- выбрана новая transcript version;
- изменилось сопоставление technical speaker → бизнес-роль;
- появился новый доверенный participant/extension/manager факт;
- разрешён конфликт источников;
- сделано ручное исправление;
- изменилась версия правил определения ролей так, что выполняется перерасчёт конкретного звонка.

Смена роли МЕНЕДЖЕР↔КЛИЕНТ считается значимым исправлением и требует проверки downstream-метрик/анализа.

## Версия псевдонимизированной транскрипции

Новая version создаётся, если меняется:

- source transcript version;
- используемая role assignment version, когда роль влияет на подготовленный текст;
- фактическое псевдонимизированное содержимое;
- правила/конфигурация псевдонимизации при осознанном перерасчёте;
- ручная privacy-коррекция.

Удаление таблицы соответствий по retention само по себе не создаёт новую псевдонимизированную транскрипцию, если её содержимое не изменилось.

## Версия privacy-пакета

Новая version нужна при изменении любого содержимого/основания, которое определяет, что именно можно отправить наружу:

- pseudonymized transcript version;
- role assignment;
- разрешённый history context;
- privacy rules/checker version при повторной валидации, если результат авторизации пакета должен отличаться;
- фактический состав внешнего пакета;
- исправление обнаруженной privacy-проблемы.

Пакет со статусом blocked не превращается в passed редактированием in place. Создаётся новая проверяемая версия/результат.

## Версия промта

Промт имеет семейство по назначению/профилю анализа.

Правила:

- draft может редактироваться до активации, если ещё не использовался как подтверждённая версия;
- после активации/использования содержимое версии неизменяемо;
- изменение инструкции создаёт новую version;
- новая активная version используется только новыми логическими анализами;
- старые анализы сохраняют ссылку на прежний prompt version;
- массовый reanalysis прошлого не запускается автоматически.

Изменение пробела/форматирования, доказанно не влияющее на смысл и фактический payload, может не требовать новой смысловой версии, но если внешний запрос реально изменился — должна существовать новая воспроизводимая версия.

## Версия методики

Новая methodology version требуется при изменении:

- набора критериев;
- применимости;
- шкалы;
- веса;
- определения этапа;
- обязательности этапа;
- правил общего балла;
- трактовки результата;
- другого правила, способного изменить оценку/метрику анализа.

Сравнение динамики между разными версиями методики должно явно учитывать version; нельзя притворяться, что шкала не менялась.

## Версия фильтра

Новая filter-rules version требуется при изменении правила, способного изменить решение принять/исключить/классифицировать звонок.

Старое решение фильтра хранит ссылку на старую version и не пересчитывается автоматически только потому, что сегодня фильтр иной.

## Идентичность модели и конфигурации

Для LLM, транскрибации, embedding и других моделей сохраняется фактически доступная идентичность:

- provider;
- model name/alias;
- reported model/version/build, если провайдер возвращает;
- adapter/config version;
- значимые параметры запроса;
- время вызова.

Если внешний провайдер использует плавающий alias и не раскрывает точный build, система не должна утверждать полную битовую воспроизводимость.

В этом случае сохраняется максимально доступная provenance и явное ограничение воспроизводимости.

Намеренная смена model/config для нового результата создаёт новую логическую операцию/версию.

## Версии знаний

### Документ

Новая document version создаётся при изменении содержимого или смысловой metadata, на которую должен ссылаться анализ.

### Fragment

Новый fragment version создаётся при:

- новой версии документа;
- изменении chunking/нормализации, влияющем на границы/текст fragment;
- исправлении fragment.

### Embedding

Новая embedding version создаётся при:

- новом fragment version;
- смене embedding model/config;
- осознанном перерасчёте.

Embedding version не заменяет document/fragment version.

### Публикация знаний

Новая publication version создаётся, когда меняется разрешённый опубликованный набор:

- добавлена/удалена версия документа;
- изменился состав разрешённых fragments;
- опубликована исправленная версия;
- изменилось правило доступности, влияющее на то, что продукт может читать.

Draft-изменения не меняют уже опубликованную publication version.

Анализ фиксирует publication version и exact fragment refs, реально переданные в LLM-контекст.

Новая публикация не переписывает исторические анализы автоматически.

## Версия контекста истории

Если анализ использует прежние разговоры, он должен ссылаться на конкретный подготовленный history context внутри privacy package/input manifest.

Изменение истории после начала анализа не меняет уже замороженный пакет.

Если позднее событие делает прежний контекст существенно неполным и требуется новый анализ, создаётся новая операция/версия.

## Версия анализа

Новая analysis version создаётся, если:

- меняется любой значимый input ref из analysis input manifest;
- выполняется разрешённый manual reanalysis;
- исправлена upstream-сущность конкретного звонка;
- изменился analysis contract/output schema так, что сохраняемый смысл результата отличается;
- исправлен результат/доказательства через процесс, который должен породить новую эффективную версию.

Новая attempt той же операции с теми же inputs не равна новой analysis version.

Подтверждённая analysis version становится неизменяемой.

## Кандидат и current analysis

Создание новой analysis version не должно немедленно уничтожать текущую.

Логика по смыслу:

1. создаётся новая operation с замороженным manifest;
2. получается/проверяется candidate result;
3. результат проходит structural/privacy/evidence checks;
4. analysis version сохраняется как подтверждённая;
5. только затем система может сделать её current по разрешённому правилу;
6. прежний current становится historical/superseded, но не удаляется.

Если новый анализ не завершился успешно, прежний current остаётся current, кроме случая, когда он отдельно invalidated из-за обнаруженной ошибки.

## Когда current может отсутствовать

Если прежний анализ признан invalidated из-за исправляющей ошибки, а новый ещё не готов, у звонка временно может не быть действующего current analysis.

В этом случае дашборд должен показывать состояние «требует перерасчёта/нет действующей версии», а не автоматически возвращать известный неверный анализ как официальный.

Точный пользовательский текст определится позднее; смысл обязателен.

## Проспективная смена конфигурации и current

Активация нового prompt/methodology/model/knowledge version для будущих звонков не invalidates автоматически current analyses старых звонков.

Они остаются корректными историческими результатами, сделанными на прежней конфигурации.

Если компания хочет пересчитать прошлый период по новой методике, это отдельная явная операция с новым набором analyses. Нельзя молча переписать историю.

## Изменение знаний

Новая publication version не делает прежний анализ «ошибочным» автоматически.

Но если исправлен факт, который был использован конкретным анализом и известно, что прежний вывод основан на неверном knowledge fragment, такой анализ может быть явно помечен кандидатом на reanalysis/invalidated по утверждённому процессу.

Массовая политика для подобных случаев относится к будущей эксплуатации и не выдумывается DOC-13.

## Изменение транскрипции/ролей конкретного звонка

Если current source transcript или role assignment исправлены по конкретному звонку и изменение может влиять на смысл анализа:

- прежний analysis manifest остаётся неизменным;
- старая analysis version остаётся в истории;
- она помечается устаревшей/invalidated относительно исправленного входа по причине;
- создаются новые pseudonymized/privacy versions;
- запускается новая analysis operation;
- current переводится на новый анализ только после успешной проверки.

Нельзя редактировать старый analysis так, будто он всегда использовал исправленную транскрипцию.

## Ручной перерасчёт

Manual reanalysis:

- имеет автора/причину;
- не является retry старой operation, если требуется новая версия результата;
- получает новый operation_id;
- фиксирует новый/явно выбранный input manifest;
- не дублирует автоматически уже доставленную обратную связь.

Решение повторно отправить feedback после нового анализа — отдельное исходящее действие/разрешение, а не следствие version switch.

## Ручное исправление итоговой оценки

Прямая correction анализа не редактирует подтверждённую старую version in place.

Допустимы только проверяемые варианты:

- создать новую analysis version с основанием correction;
- сохранить отдельное override/correction event, которое явно участвует в effective view.

UX-границы и права Павла/руководителя определены в [DASHBOARD_ADMIN](DASHBOARD_ADMIN.md). История исходного AI result сохраняется в обоих вариантах.

## Версионирование и delivery

Создание новой analysis version не меняет историю уже отправленного сообщения.

Outgoing action всегда ссылается на конкретную analysis version.

Если появляется новый current analysis:

- прежняя доставка остаётся фактом;
- новое сообщение не создаётся автоматически;
- повторная/обновлённая обратная связь требует отдельного разрешённого outgoing action.

## Версионирование и CRM-факты

Подтверждение CRM/человека не является новой версией AI analysis.

Новый CRM-факт добавляется отдельно.

Исправление/отмена CRM-факта хранится как новая история/корректирующее событие по модели источника и не переписывает AI manifest.

## Версионирование и retention

Удаление содержимого по законной/утверждённой retention policy не означает, что версия «никогда не существовала».

Для исторического результата по возможности сохраняются безопасные metadata:

- version_id;
- provenance;
- связи;
- время;
- deletion state/reason;
- ссылки на downstream results.

Нельзя сохранять запрещённое содержимое только ради воспроизводимости, если срок хранения истёк.

Уровень воспроизводимости после удаления должен быть честно ограничен.

## current не определяется максимальным номером

Нельзя считать current по правилу «самая большая version_number» без проверки состояния.

Более новая версия может быть:

- draft;
- blocked;
- failed;
- candidate;
- invalidated.

Current выбирается только среди допустимых подтверждённых версий по правилам конкретного семейства.

## Конкурентные обновления

Если два процесса одновременно создают новые candidate versions:

- обе попытки могут быть зарегистрированы;
- current switch должен разрешиться однозначно;
- проигравший candidate не должен молча переписать current после более нового/разрешённого выбора;
- история обеих попыток сохраняется.

Точный locking/SQL-механизм выбирается при реализации.

## Анализ и воспроизводимость

Уровни воспроизводимости нужно различать.

### Логическая воспроизводимость

Можно точно установить inputs, versions, provider/model identity, prompt, knowledge, output contract и сохранённый result.

Это обязательно.

### Повторный вычислительный результат

Повторный вызов модели может вернуть отличающийся текст даже на тех же inputs из-за недетерминированности или изменений провайдера.

Система не обещает идентичный token-by-token output, если провайдер/модель этого не гарантирует.

Поэтому оригинальный подтверждённый AI response/result и его provenance должны сохраняться в разрешённых границах.

## Миграция формата версии

Если в будущем меняется storage schema или contract, старый version_id не теряет смысл.

Миграция данных не должна выдавать старую версию за вновь вычисленный результат.

Если содержимое трансформировано технически без изменения бизнес-смысла, сохраняется provenance миграции.

## Обязательные проверки DOC-13

Будущая реализация должна подтвердить как минимум:

1. Исправление transcript создаёт новую version, старая не меняется.
2. Retry той же transcription operation до подтверждённого результата не создаёт лишнюю semantic version.
3. Смена model/config при новом transcribe создаёт новый provenance/version даже при совпавшем тексте.
4. Исправление роли создаёт новую role assignment version.
5. Новая role version порождает новый downstream privacy/analysis chain, если влияет на анализ.
6. Privacy package blocked не редактируется в passed; создаётся новая проверяемая версия.
7. Изменение prompt после его использования создаёт новую version.
8. Analysis, начатый на prompt v1, не переключается на v2 посреди выполнения.
9. Изменение methodology weights создаёт новую methodology version.
10. Старый analysis продолжает ссылаться на старую methodology version.
11. Новая knowledge publication не переписывает старый analysis.
12. Analysis хранит exact fragment refs, реально переданные в LLM.
13. Смена embedding model создаёт новую embedding provenance/version.
14. Новый analysis candidate не становится current до успешной проверки.
15. Failed candidate не снимает валидный current.
16. Invalidated current может оставить звонок без действующего анализа до успешного reanalysis.
17. Проспективная активация новой модели не заставляет автоматически пересчитать всю историю.
18. Manual reanalysis создаёт новую operation/version, а не retry старой.
19. Новый current analysis не отправляет повторно feedback без отдельного outgoing action.
20. CRM confirmation не создаёт новую AI analysis version.
21. Retention deletion сохраняет безопасную историю version/provenance без запрещённого содержимого.
22. current выбирается не простым max(version_number).
23. Два конкурентных candidate не могут оба стать current одного семейства.
24. По любому analysis можно восстановить полный input manifest.
25. Если provider не раскрывает точный model build, система показывает ограничение воспроизводимости, а не выдумывает version.
26. Исторический dashboard result можно объяснить версиями, действовавшими именно для этого analysis, а не сегодняшними current settings.

## Что не определяется DOC-13

- SQL-механизм current pointer;
- sequence/UUID implementation;
- transaction/locking syntax;
- конкретные hashes;
- численные сроки хранения;
- политика массового reanalysis после обновления знаний/методики;
- UX ручного override;
- физическая evidence schema; логические требования определены в [EVIDENCE_MODEL](EVIDENCE_MODEL.md);
- admin permissions DOC-16.

## Критерий DOC-13

Документ готов, если:

- для каждой основной версионной сущности понятно, что создаёт новую version;
- retry отделён от нового versioned result;
- подтверждённые versions immutable;
- current отделён от «самая новая»;
- prospective change не переписывает историю;
- corrective change может invalidate зависимый current и требует downstream recomputation;
- analysis имеет полный immutable input manifest;
- old result сохраняет точную комбинацию transcript/roles/privacy/prompt/methodology/model/knowledge/contract;
- history и delivery не переписываются при переключении current;
- ограничения реальной воспроизводимости внешних моделей зафиксированы честно.

SQL, n8n, Supabase, сервер и production в DOC-13 не изменялись.
