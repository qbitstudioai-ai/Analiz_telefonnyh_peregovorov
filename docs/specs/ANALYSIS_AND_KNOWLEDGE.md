# Анализ разговора и база знаний компании

## Два слоя анализа

Анализ настраивается двумя разными способами:

1. **Промт анализа** — определяет, что и как проверять.
2. **База знаний компании** — содержит факты, правила и документацию, с которыми сравниваются слова менеджера.

Эти слои не должны смешиваться.

## Промт анализа

Промт может задавать этапы разговора, критерии оценки, обязательные действия менеджера, шкалу, правила формирования рекомендаций и формат результата.

Промт является настройкой компании и не должен требовать изменения CORE.

## База знаний

Для проверки фактической корректности слов менеджера система должна опираться на документацию компании: технические характеристики, цены, условия продажи, регламенты, инструкции, скрипты, допустимые и запрещённые обещания, FAQ и другие материалы.

LLM не должна считать свои общие знания главным источником фактов о конкретной компании.

## Разделение методики и фактов

Промт отвечает: **что проверять и как оценивать?**

База знаний отвечает: **какие факты и правила компании являются правильными?**

Например, промт требует проверить срок гарантии, а правильный срок должен поступать из документации компании, а не быть жёстко записан в промте.

## Единый источник знаний компании

Принятое правило:

- у одной компании должен быть единый актуальный источник знаний для бота первичного обращения, анализа звонков и будущих продуктов;
- workflow этих продуктов независимы;
- каждый продукт получает только разрешённые **опубликованные** знания своей компании;
- доступ каждого продукта к знаниям должен идти через отдельные ограниченные права;
- результат анализа звонка должен сохранять версию знаний, на которой сделан вывод.

Не нужно без необходимости создавать независимые копии одной и той же документации для разных продуктов.

Точный механизм публикации, версий, прав и совместного доступа пока не выбран и будет описан отдельными задачами.

## Векторное хранилище

Теоретически может использоваться существующее векторное хранилище Supabase компании.

На текущем этапе фиксируются только требования:

- продукт получает только знания своей компании;
- используются актуальные разрешённые опубликованные материалы;
- разные независимые продукты могут обращаться к одному источнику знаний;
- документы другой компании недоступны;
- обновление знаний не требует ручного копирования фактов в каждый промт;
- сохранённый результат анализа позволяет установить, какая версия знаний использовалась.

Точные schema, таблицы, embeddings, chunking и поиск определяются позднее.

## Доказательность

Если система утверждает, что менеджер ошибся в факте компании, должно быть возможно понять, на каком материале основан вывод.

Нужно различать факт из разговора, факт из документации, оценку модели и рекомендацию модели.

Будущая спецификация доказательств должна связать вывод как минимум с цитатой/фрагментом разговора, таймкодом при наличии, правилом оценки и документом/версией знаний, если вывод основан на документации.
