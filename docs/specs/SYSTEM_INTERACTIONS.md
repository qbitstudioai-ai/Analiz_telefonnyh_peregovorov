# Взаимодействие инструментов как единого продукта

Статус: согласованная архитектура верхнего уровня. Документ определяет ответственность компонентов и движение данных без нод n8n, SQL, окончательных таблиц, payload и выбора библиотек.

## Общий принцип

Продукт не является одним большим workflow. Это связанная система, в которой каждый инструмент выполняет свою роль:

- источники сообщают о звонках и предоставляют доступное аудио;
- n8n управляет последовательностью действий и внешними интеграциями;
- Supabase хранит подтверждённое состояние и историю;
- сервис транскрибации/диаризации превращает временное аудио в структурированный разговор;
- аналитическая LLM предлагает оценку по промту и знаниям;
- CORE проверяет результат и только затем сохраняет его;
- серверная часть дашборда безопасно читает подготовленные данные;
- браузер руководителя показывает результат, но не является хранилищем;
- выходной адаптер доставляет обратную связь менеджеру.

Если n8n перезапустился или внешний сервис недоступен, продолжение определяется сохранённым состоянием Supabase, а не памятью текущего запуска.

## Развёртывание для нескольких компаний

Общая серверная инфраструктура может обслуживать несколько компаний:

- одна установка n8n с отдельными экземплярами настроек, Credentials и процессов компаний;
- одна серверная установка Supabase/PostgreSQL;
- общий вычислительный сервис транскрибации/диаризации, если испытания подтверждают его пригодность;
- подключённые LLM/embedding-сервисы;
- общий технический мониторинг.

У каждой компании отдельны:

- schema Supabase и ограниченные права;
- настройки, источники, фильтры, сотрудники и критерии оценки;
- Credentials источников и каналов доставки;
- экземпляр или набор workflow продукта;
- опубликованные знания компании;
- отдельный дашборд со своей серверной частью, доменом и оформлением;
- test и production-контуры/идентификаторы.

Точное число workflow не фиксируется до технического проектирования. Логические обязанности должны сохраняться независимо от того, реализованы они одним или несколькими workflow.

## Карта компонентов

| Компонент | Отвечает за | Не является источником истины для |
|---|---|---|
| CRM, телефония, кабинет оператора | Событие звонка, внешний ID, доступное аудио, подтверждённые данные контакта/сделки и фактические статусы CRM | Внутреннего процесса анализа |
| Входной адаптер | Проверка источника, приведение события к общему смыслу, получение метаданных и аудио | Бизнес-оценки менеджера |
| n8n | Оркестрация, порядок шагов, вызовы сервисов, контролируемые повторы и маршрутизация | Долговременной истории и единственной памяти процесса |
| Временное файловое хранилище | Аудио на время разрешённой обработки | Постоянного архива звонков |
| Транскрибация и диаризация | Реплики, таймкоды, технические speaker и показатели качества | Идентичности клиента, результата продажи и окончательной оценки |
| CORE | Фильтрация правил, анонимизация, сбор контекста, проверка структуры ответа LLM, применение разрешённых переходов | Секретов и настроек, присланных пользователем/LLM |
| Аналитическая LLM | Предложенная оценка, выводы, рекомендации и предполагаемый результат по предоставленному контексту | Подтверждённой продажи, прав доступа, адресата и состояния выполнения |
| Supabase | Зарегистрированные события, связи, состояния, транскрипции, версии, анализы, доказательства, исходящие действия и подтверждения | Постоянного аудио |
| Сервер дашборда | Авторизация, ограниченные запросы, подготовка метрик и выдача данных своей компании | Первичных фактов и секретов в браузере |
| Браузер дашборда | Навигация, фильтры и визуальное представление | Расчёта скрытых альтернативных формул и прямого доступа к БД |
| Выходной адаптер | Отправка в Bitrix24, Telegram или другой канал и получение доступного подтверждения | Решения повторить неопределённую отправку без сверки |
| Мониторинг | Обнаружение остановок, задержек и технических ошибок | Изменения бизнес-результатов звонка |

## Сквозная схема

~~~mermaid
flowchart TD
    A["CRM / телефония / оператор"] --> B["Входной адаптер и n8n"]
    B --> C["Supabase: состояние и история"]
    B --> D["Транскрибация и диаризация"]
    D --> B
    C --> B
    B --> E["LLM: анализ по промту и знаниям"]
    E --> B
    B --> C
    C --> F["Сервер дашборда"]
    F --> G["Дашборд руководителя"]
    B --> H["Bitrix24 / Telegram менеджера"]
    H --> B
~~~

Стрелка не означает, что внешний сервис может сам менять произвольные данные. Каждый результат возвращается в n8n/CORE, проверяется и сохраняется с версией и состоянием.

## Источники истины

| Факт | Главный источник | Что сохраняется в Supabase |
|---|---|---|
| Событие и внешний ID звонка | Источник звонка | Полученный снимок, время приёма и состояние обработки |
| Принадлежность менеджеру/контакту/сделке | Подтверждённые ID источника/CRM | Ссылки и история их изменений |
| Аудио | Источник; временная копия продукта | Метаданные временного файла и факт удаления, но не постоянный файл |
| Транскрипция и роли | Выбранный сервис после проверки CORE | Версия текста, сегменты, качество и происхождение |
| Промт и шкала | Настройка компании | Использованная версия |
| Факты компании | Опубликованный источник знаний | Версия знаний и фрагменты-доказательства |
| Оценка и рекомендация | Проверенный результат анализа | Полный версионированный результат и доказательства |
| Предполагаемый исход разговора | Анализ разговора | Вывод, уверенность, цитата/таймкод |
| Фактический замер, договор, оплата | CRM или подтверждение человека | Полученное подтверждение, источник и время |
| Отправка обратной связи | Канал доставки | Исходящее действие, попытки и подтверждённый/неизвестный результат |
| Метрики | Согласованные правила над сохранёнными фактами | Версия определения и данные для воспроизводимого расчёта |

Дашборд не записывает новую версию факта только потому, что пользователь открыл или отфильтровал страницу. Ручное исправление создаёт отдельное проверяемое событие с автором и причиной.

## Основной поток данных

### Обычный клиентский разговор

1. Адаптер получает событие.
2. n8n регистрирует событие и состояние в Supabase.
3. После защиты от дубля CORE применяет фильтр.
4. n8n получает аудио во временное хранилище и вызывает транскрибацию/диаризацию.
5. CORE проверяет результат, назначает роли и анонимизирует текст.
6. Из Supabase берутся разрешённые опубликованные знания и краткий обезличенный контекст прежних звонков.
7. LLM получает только подготовленный контекст и возвращает структурированное предложение анализа.
8. CORE проверяет допустимые значения; Supabase сохраняет версию анализа и доказательства.
9. Сохранённые данные становятся доступны серверу дашборда.
10. n8n создаёт исходящее действие, отправляет обратную связь и отдельно сохраняет результат доставки.
11. Временное аудио удаляется по согласованному правилу.

### Исключённый звонок

Событие и причина сохраняются. Получение аудио, LLM и оценка не запускаются, если фильтра достаточно. Дашборд показывает звонок отдельной категорией.

### Пропущенный звонок

Событие сохраняется без ожидания аудио. Следующий подтверждённый звонок может быть связан как обратный. Дашборд показывает время до перезвона.

### Повторный звонок

Supabase связывает новый звонок с известным клиентом/сделкой по доверенным идентификаторам. n8n передаёт LLM краткий обезличенный контекст. Старые звонки и оценки не переписываются.

## Контрольные точки

До затратного или внешнего действия должно существовать сохранённое основание:

- до скачивания/обработки аудио — зарегистрированное событие;
- до LLM — сохранённая версия подготовленной транскрипции и контекста;
- до отправки менеджеру — сохранённый анализ и исходящее действие;
- до повторной попытки — сохранённый статус предыдущей попытки;
- до показа метрики — сохранённые факты и версия определения показателя.

Нельзя держать единственную копию значимого результата только внутри выполнения n8n.

## Единая база знаний и независимые продукты

Знания принадлежат компании, а не конкретному workflow. Бот первичного обращения и анализ звонков могут читать один опубликованный набор компании через разные ограниченные права.

При этом:

- продукты не вызывают workflow друг друга;
- сбой одного продукта не останавливает другой;
- продукт не видит данные другой компании;
- анализ хранит точную версию знаний, использованную для вывода;
- черновики и архивные знания не становятся доступными клиентскому анализу без публикации.

Техническое размещение таблиц и функций будет определено позже, но не должно создавать ручные копии одного документа для каждого продукта.

## Дашборд

Для каждой компании разворачивается отдельный дашборд с серверной частью. Браузер не получает пароль PostgreSQL, служебные ключи Supabase или Credentials n8n.

Сервер дашборда:

- проверяет пользователя и его компанию;
- получает только разрешённые звонки, транскрипции, доказательства и метрики;
- применяет согласованные определения показателей;
- записывает разрешённые ручные исправления через отдельные операции;
- журналирует административные изменения.

Будущий ИИ-помощник руководителя обращается к тем же ограниченным подготовленным данным через серверный слой, а не получает произвольный административный доступ к Supabase.

## CORE, настройки и адаптеры

**CORE:** порядок обработки, проверка результатов, анонимизация, жизненный цикл, версионирование, доказательность, надёжность и общие правила метрик.

**Настройки компании:** источники, фильтры, сотрудники, типы звонков, промты, шкалы/веса, каналы обратной связи, часовой пояс и допустимые знания.

**Адаптеры:** конкретные API источника звонков, транскрибации/LLM, CRM, Bitrix24, Telegram и других каналов.

Обычное внедрение меняет настройки, Credentials и подключённые адаптеры. Изменение CORE является новой версией шаблона.

## Что пока не определяется

- число и состав workflow;
- точные форматы событий и ответов;
- таблицы, столбцы, SQL и функции;
- очередь, блокировки и retry-алгоритмы;
- конкретный движок транскрибации/диаризации;
- конкретная LLM и модель embeddings;
- технология серверной части дашборда;
- сроки хранения и численные пороги.

Эти решения принимаются последующими задачами после проверки требований.

## Критерий готовности будущей реализации

По одному ID звонка должно быть возможно определить: откуда пришло событие, где находится текущее состояние, какая версия транскрипции/промта/знаний/анализа использована, доступен ли результат дашборду, создавалась ли обратная связь, подтверждена ли доставка и удалена ли временная копия аудио.
