# Контракты обмена между компонентами

Статус: DOC-11. Документ фиксирует обязательный логический смысл запросов, ответов, идентификаторов, статусов и подтверждений между компонентами продукта.

Это не JSON workflow n8n, не SQL, не окончательные HTTP routes и не описание конкретных библиотек. Реализация может использовать HTTP, очередь, локальный вызов или другой транспорт, но обязана сохранять смысл контрактов ниже.

## Цель

По любому звонку и любой значимой операции должно быть возможно однозначно установить:

- к какой компании и среде относится операция;
- к какому событию и логическому звонку она относится;
- какая именно операция выполнялась и какая это попытка;
- какие версии входных артефактов использованы;
- был ли запрос принят, отклонён или признан дублем;
- завершилась ли операция подтверждённым успехом, безопасной ошибкой, ошибкой конфигурации или неизвестным результатом;
- какой результат сохранён до перехода к следующему затратному/внешнему шагу;
- какое подтверждение вернул внешний сервис;
- можно ли безопасно повторить операцию.

Контракт не должен позволять одному компоненту незаметно менять компанию, среду, идентичность звонка, подтверждённый факт или версию входов.

## Связанные правила

DOC-11 не заменяет:

- [CALL_LIFECYCLE](CALL_LIFECYCLE.md) — жизненный цикл звонка;
- [RELIABILITY_AND_IDEMPOTENCY](RELIABILITY_AND_IDEMPOTENCY.md) — дубли, идемпотентность и восстановление;
- [ACCESS_AND_ISOLATION](ACCESS_AND_ISOLATION.md) — компания + среда и права доступа;
- [TRANSCRIPTION_AND_PRIVACY](TRANSCRIPTION_AND_PRIVACY.md) — транскрипция, роли и privacy-gate;
- [ANALYSIS_AND_KNOWLEDGE](ANALYSIS_AND_KNOWLEDGE.md) — промт, знания и аналитика;
- будущий DOC-12 — физический словарь сущностей/полей Supabase;
- будущий DOC-13 — полные правила версионирования;
- будущий DOC-14 — модель доказательств.

## Три уровня подтверждения

Нельзя смешивать три разных факта.

### 1. Транспортное подтверждение

Означает только, что запрос технически дошёл до принимающей стороны или что соединение вернуло ответ.

HTTP 200, успешный сетевой вызов или отсутствие исключения сами по себе не доказывают бизнес-успех.

### 2. Решение по контракту

Принимающая сторона должна однозначно классифицировать запрос:

| Решение | Смысл |
|---|---|
| accepted | Контракт валиден, запрос относится к разрешённому контуру и может исполняться |
| duplicate | Та же логическая сущность/операция уже известна; новый независимый эффект не создаётся |
| rejected | Запрос нарушает контракт, права, обязательные условия или business-gate; исполнение не начинается |

При duplicate возвращается ссылка на уже известную сущность/операцию и её текущее состояние, если это безопасно и разрешено.

При rejected сохраняется машинно-различимая причина. Отклонённый контракт не маскируется как временная техническая ошибка.

### 3. Итог операции

Даже accepted не означает, что внешняя или затратная операция завершилась успешно.

Для каждой значимой операции используется состояние по [RELIABILITY_AND_IDEMPOTENCY](RELIABILITY_AND_IDEMPOTENCY.md):

| Канонический код | Смысл |
|---|---|
| not_started | Операция ещё не начиналась |
| in_progress_unconfirmed | Запрос начат, окончательный результат ещё не подтверждён и не сохранён |
| succeeded | Полезный результат проверен и надёжно сохранён |
| failed_retryable | Известно, что полезный результат не получен и контролируемый повтор безопасен |
| failed_requires_fix | Повтор без изменения условий не поможет |
| outcome_unknown | Запрос мог выполниться, но надёжного подтверждения нет |

Эти коды относятся к операции, а не заменяют состояния звонка, результат продажи или статус доставки.

## Каноническая обёртка внутренней операции

Названия ниже — канонические логические поля. Транспорт может технически называться иначе, но адаптер обязан однозначно сохранить их смысл.

| Поле | Назначение |
|---|---|
| contract_version | Версия логического контракта границы |
| scope_ref | Внутренняя ссылка на контур «компания + среда» |
| call_ref | Внутренний ID логического звонка после его регистрации |
| operation_id | Стабильная идентичность одной логической операции |
| attempt_id | ID конкретной попытки выполнения этой операции |
| operation_type | Тип операции: транскрибация, анализ, отправка и т.п. |
| correlation_id | Сквозная техническая трассировка; не является бизнес-ID или правом доступа |
| input_refs | Ссылки на используемые входные артефакты и их версии |
| requested_at | Время создания запроса системой |
| decision | accepted, duplicate или rejected после проверки контракта |
| operation_state | Одно из состояний операции выше |
| result_ref | Ссылка на подтверждённо сохранённый результат, если он существует |
| external_request_ref | ID запроса/операции внешнего провайдера, если он был выдан |
| error_class | Машинная категория ошибки, если операция не успешна |
| error_code | Более точный код адаптера/контракта без секретов и сырых персональных данных |
| completed_at | Время подтверждённого окончания операции, если применимо |

attempt_id меняется при новой попытке. operation_id при безопасном повторе той же логической операции остаётся тем же.

correlation_id нужен для диагностики и не может использоваться вместо call_ref, operation_id или доверенной идентичности источника.

## Контур компании и среды

scope_ref для обычной runtime-операции определяется серверной конфигурацией и Credential по [ACCESS_AND_ISOLATION](ACCESS_AND_ISOLATION.md).

Обязательные правила:

- внешний payload не может назначить или переключить scope_ref;
- если событие содержит company/tenant/schema, это только проверяемое входное значение, а не источник права;
- внутренний scope_ref должен совпадать с Credential вызывающего сервиса;
- call_ref, input_refs и result_ref должны принадлежать тому же контуру;
- несовпадение контура даёт rejected, а не автоматическое переключение;
- неизвестный контур не заменяется default или production.

## Идентичности не взаимозаменяемы

Нужно отдельно хранить и передавать по назначению:

- внешний ID события источника;
- внешний стабильный ID звонка источника;
- аккаунт/подключение источника;
- внутренний call_ref;
- operation_id;
- attempt_id;
- ID запроса внешнего провайдера;
- ID исходящего действия;
- ID сообщения/доставки канала.

Один из этих идентификаторов нельзя молча использовать вместо другого.

Внешний ID звонка уникален только внутри области, определённой DOC-04: компания + адаптер источника + конкретное подключение/аккаунт + внешний ID.

Если источник не предоставляет надёжный стабильный ID, его адаптер до production обязан иметь отдельно утверждённую проверяемую стратегию идентичности. DOC-11 не выдумывает универсальный surrogate из телефона и времени.

## Версии входов

Любая операция, результат которой зависит от изменяемого входа, должна сохранять ссылки на фактически использованные версии.

Минимально по смыслу:

- версия/идентичность аудиоартефакта;
- версия транскрипции;
- версия назначения ролей/подготовленного privacy-пакета;
- версия промта;
- версия методики/критериев;
- версия модели/провайдера;
- версия опубликованных знаний;
- версия контекста истории, если он использован;
- версия контракта ответа.

Полный состав и правила создания новых версий определит DOC-13. DOC-11 требует только не терять эту связь на границах.

## Порядок проверки входного запроса

До запуска затратной или внешней операции принимающий компонент проверяет по смыслу:

1. вызывающая сервисная идентичность разрешена;
2. контур определён и совпадает с Credential;
3. contract_version поддерживается;
4. обязательные ID присутствуют и относятся к одному контуру;
5. необходимые входные артефакты существуют и имеют ожидаемое состояние;
6. операция с тем же operation_id не имеет уже подтверждённого результата;
7. не существует конфликтующей активной попытки, если параллельность запрещена;
8. выполнены профильные gates — например privacy-gate перед внешней LLM;
9. контрольная точка/намерение сохранены до внешнего эффекта.

Если контрольную точку сохранить нельзя, внешний шаг не выполняется.

## Контракт 1. Источник → входной адаптер / n8n

Источник может прислать webhook, callback, событие опроса или другой сигнал.

### Вход по смыслу

Адаптер должен уметь извлечь или определить:

- тип источника/адаптера;
- конкретное серверно настроенное подключение источника;
- внешний ID события, если источник его предоставляет;
- внешний стабильный ID звонка, если источник его предоставляет;
- тип/стадию события;
- время события у источника;
- направление и подтверждённый статус ответа, если доступны;
- доверенные participant/extension/manager/CRM-ссылки, если доступны;
- признак/ссылку готовности аудио, если доступны;
- иные разрешённые метаданные, необходимые фильтрации и связи.

Токен источника, пароль и secret webhook не являются полями бизнес-события.

### Результат приёма

До дорогих этапов система должна вернуть/сохранить по смыслу:

- decision;
- внутренний ID зарегистрированного события;
- call_ref, если звонок уже разрешён;
- признак, является ли это дублем события или новым событием уже известного звонка;
- текущее состояние звонка;
- машинную причину отклонения/фильтра, если применимо.

duplicate не создаёт второй звонок или вторую обработку.

Новое позднее событие того же звонка не считается дублем только потому, что call_ref уже существует.

## Контракт 2. Получение и готовность аудио

Запрос на аудио связывается с:

- call_ref;
- operation_id;
- доверенным источником/подключением;
- внешним ID звонка или разрешённой ссылкой источника;
- текущим состоянием доступности записи.

Результат должен различать как минимум:

- аудио ещё не доступно;
- аудио получено и проверено как готовый локальный артефакт;
- полезный результат не получен, повтор разрешён;
- конфигурационная/постоянная ошибка;
- результат получения неизвестен.

Перед транскрибацией сохраняется ссылка на готовый локальный аудиоартефакт/его версию и признаки проверки целостности по [AUDIO_RETENTION](AUDIO_RETENTION.md).

Неполный файл не повышается до готового аудио.

## Контракт 3. n8n / CORE → сервис транскрибации и диаризации

### Запрос

Минимальный смысл запроса:

- общая обёртка операции;
- ссылка на локальный готовый аудиоартефакт;
- версия/идентичность аудио;
- разрешённые параметры обработки из серверной конфигурации;
- требование получить technical speaker и таймкоды;
- идентичность/версия выбранного движка и его конфигурации, когда она будет утверждена.

Сырой звук не отправляется во внешний контур в принятой архитектуре.

### Ответ

Сервис возвращает по смыслу:

- тот же operation_id и текущий attempt_id;
- фактически использованный движок/модель/конфигурацию;
- ссылку/версию результата транскрибации;
- сегменты;
- technical speaker;
- начало/конец сегментов;
- распознанный текст;
- доступные показатели качества/служебные метрики;
- состояние операции и ошибку, если есть.

Технический speaker не считается автоматически ролью МЕНЕДЖЕР/КЛИЕНТ.

Ответ считается succeeded только после проверки структуры результата CORE и надёжного сохранения нужного артефакта/версии.

## Контракт 4. Назначение ролей и privacy-подготовка

До аналитической LLM локальный контур формирует отдельный подготовленный пакет.

Пакет должен быть связан с:

- call_ref;
- версией исходной транскрипции;
- версией/результатом назначения ролей;
- версией псевдонимизированной транскрипции;
- разрешённым контекстом прежних звонков, если он нужен;
- результатом privacy-проверки.

Privacy-проверка имеет два логических результата:

- passed — внешний LLM-вызов может быть рассмотрен;
- blocked — внешний LLM-вызов не выполняется.

blocked не превращается в автоматическую отправку исходного текста как fallback.

Подготовленный внешний пакет не содержит исходное аудио, исходную транскрипцию, таблицу соответствия псевдонимов, реальные CRM ID человека, телефоны, email, адреса, Credentials, имя schema или секреты.

## Контракт 5. Получение знаний для анализа

Запрос знаний выполняется отдельной ограниченной ролью своей компании/среды.

Запрос должен быть связан с:

- call_ref/операцией анализа;
- продуктом;
- контуром;
- публикацией/версией знаний;
- псевдонимизированным поисковым контекстом;
- параметрами поиска, которые позже будут версионированы при необходимости.

Результат содержит только разрешённые опубликованные материалы своей компании:

- ссылки/ID фрагментов;
- содержимое разрешённых фрагментов;
- документ/источник;
- версию публикации знаний;
- данные, нужные будущей доказательности.

Черновики и знания другой компании не являются допустимым пустым «шумом» результата — они технически недоступны по DOC-10.

## Контракт 6. CORE / n8n → аналитическая LLM

LLM вызывается только после успешного privacy-gate.

### Запрос

Минимально пакет анализа содержит:

- operation_id и attempt_id для корреляции внутри адаптера;
- версию контракта ожидаемого ответа;
- псевдонимизированный текущий разговор;
- роли и разрешённые таймкоды/ссылки на сегменты;
- минимальный релевантный псевдонимизированный контекст истории;
- версию промта;
- версию методики/критериев;
- разрешённые опубликованные знания и их версию;
- безопасные ID фрагментов разговора/знаний для ссылок в доказательствах;
- требуемую структуру ответа.

Внешняя LLM не получает scope_ref в форме, раскрывающей внутреннюю schema/инфраструктуру, и не получает Credentials.

### Ответ

Ответ LLM — предложение анализа, а не подтверждённый бизнес-факт.

Он должен позволять CORE установить:

- к какому запросу относится ответ;
- фактически использованную модель/провайдера, насколько это возвращает адаптер;
- прошёл ли ответ структурную проверку;
- оценки применимых критериев;
- наблюдения, сильные стороны, ошибки и рекомендации;
- предполагаемый результат разговора;
- доказательственные ссылки на переданные сегменты/фрагменты;
- доступную уверенность там, где методика её требует;
- технические предупреждения/ограничения ответа.

LLM не может своим ответом:

- сменить компанию/среду;
- назначить подтверждённую продажу;
- изменить адресата исходящего сообщения;
- выбрать schema;
- выдать произвольный текст за сохранённую цитату, если ссылка не подтверждается входным пакетом;
- напрямую записать результат в Supabase.

CORE проверяет структуру, допустимые значения, ссылки на доказательства и privacy ответа до сохранения подтверждённой версии анализа.

Невалидный ответ не считается succeeded.

## Контракт 7. Сохранение результата в Supabase

Supabase является источником истины для подтверждённого состояния продукта.

Каждая значимая запись результата должна быть связана по смыслу с:

- scope_ref;
- call_ref;
- operation_id;
- использованными input_refs;
- версией создаваемого результата;
- происхождением результата;
- состоянием операции;
- временем сохранения.

Перед следующим затратным/внешним шагом текущий значимый результат должен быть сохранён.

Если ответ на запись потерян, система сначала сверяет наличие результата по ожидаемой идентичности и только затем решает, нужна ли повторная запись.

Нельзя создавать вторую равнозначную версию только из-за потерянного ответа БД.

## Контракт 8. Supabase → сервер дашборда

Браузер напрямую с БД не работает.

Запрос серверной части дашборда должен определять:

- подтверждённого пользователя/его разрешённую область;
- scope_ref из серверной авторизации, а не из произвольного URL;
- требуемое представление/операцию;
- фильтры;
- период;
- пагинацию/сортировку, если применимо.

Ответ содержит только разрешённые данные этого контура и должен сохранять различимость:

- подтверждённых фактов;
- ИИ-предположений;
- статуса качества/надёжности;
- версии анализа;
- подтверждённого CRM-результата;
- состояния доставки обратной связи.

Подстановка ID объекта другой компании не раскрывает факт существования, содержимое или агрегаты чужого контура.

Таблица соответствия псевдонимов и служебные Credentials браузеру не выдаются.

## Контракт 9. Подтверждение фактического результата CRM / человеком

Подтверждённый замер, договор, оплата, продажа или другой бизнес-факт не берётся из предложения LLM.

Контракт подтверждения должен содержать по смыслу:

- доверенный источник подтверждения;
- ссылку на контакт/сделку/звонок в разрешённом контуре;
- тип подтверждённого факта;
- значение/статус;
- время факта или время получения подтверждения;
- происхождение и, где применимо, автора ручного подтверждения.

Полученное подтверждение создаёт отдельный факт. Оно не переписывает бесследно прежний ИИ-вывод.

## Контракт 10. Создание исходящего действия

До отправки обратной связи создаётся и сохраняется отдельное исходящее действие.

Оно связано с:

- scope_ref;
- call_ref;
- подтверждённой версией анализа;
- типом назначения;
- настроенным каналом;
- доверенно определённым получателем/адресатом;
- версией/содержимым сообщения;
- operation_id отправки.

Адресат и канал определяются серверной конфигурацией и доверенными данными, а не текстом ответа LLM.

Одинаковая версия анализа и то же назначение не создают второе равнозначное исходящее действие при повторном событии.

## Контракт 11. n8n → выходной канал и подтверждение доставки

### Запрос на отправку

Перед внешним вызовом исходящее действие уже существует в Supabase.

Адаптер получает:

- ID исходящего действия;
- operation_id и attempt_id;
- серверно выбранный Credential канала;
- разрешённого получателя;
- подготовленное сообщение;
- внешний idempotency key, если конкретный канал его надёжно поддерживает.

### Ответ канала

Адаптер сохраняет доступные сведения:

- ID запроса/сообщения провайдера;
- транспортный результат;
- подтверждённый провайдером статус;
- время отправки/доставки, если достоверно доступно;
- код ошибки;
- возможность безопасного повтора;
- сырой ответ только в разрешённом минимальном виде без секретов.

Статус канала нормализуется без завышения доказательности.

«API принял запрос» не превращается автоматически в «доставлено», если конкретный провайдер этого не гарантирует.

Если доставка подтверждена, та же операция повторно не отправляется.

Если запрос мог уйти, но подтверждение потеряно, состояние — outcome_unknown / «доставка неизвестна». Слепая повторная отправка запрещена до сверки.

## Ошибки

Контракт ошибки должен позволять машине принять решение без чтения человеческого текста.

Минимально различаются по смыслу:

- ошибка временной доступности/лимита, которая может допускать повтор;
- ошибка авторизации/истёкшей Credential;
- ошибка конфигурации;
- неподдерживаемая версия контракта;
- невалидный обязательный вход;
- нарушение контура/прав;
- privacy-block;
- невалидный/непроверяемый ответ модели;
- конфликт уже существующего результата;
- внешний результат неизвестен.

Человеческое описание допускается как дополнение, но не заменяет error_class/error_code.

Тексты ошибок и логи не должны содержать секреты, таблицу соответствия или полные исходные транскрипции.

## Таймауты

Таймаут — техническое наблюдение, а не автоматическое доказательство failed_retryable.

Если запрос гарантированно не достиг внешнего сервиса и полезный результат невозможен, адаптер может классифицировать безопасную повторяемую ошибку.

Если запрос мог быть выполнен, но ответ потерян, применяется outcome_unknown до сверки.

Конкретные численные таймауты и retry-политики являются параметрами адаптеров и будут определяться/испытаны при реализации.

## Повторы и дубли

При повторе того же логического запроса:

- сохраняется тот же operation_id;
- создаётся новый attempt_id, если фактически выполняется новая попытка;
- уже подтверждённый succeeded возвращается как известный результат и не выполняется заново;
- duplicate входного события не создаёт новую операцию;
- failed_retryable допускает новую попытку по политике адаптера;
- failed_requires_fix не запускает автоматический повтор;
- outcome_unknown сначала требует сверки фактического результата;
- изменение значимых входных версий может потребовать новую логическую операцию/версию результата, что окончательно определит DOC-13.

## Совместимость версий контракта

Каждая граница должна иметь contract_version.

Изменение считается несовместимым, если компонент больше не может однозначно понять обязательный смысл поля, статуса или результата.

До production реализация должна определить правила совместимости и порядок обновления обеих сторон.

Компонент не должен «угадывать» неизвестную несовместимую версию. Такой запрос отклоняется с машинным кодом.

## Что запрещено передавать как управляющее решение

Следующие значения нельзя принимать как авторитетную команду только потому, что они находятся во внешнем payload/LLM-тексте:

- company/schema/tenant;
- Credential/секрет;
- роль доступа;
- подтверждённый факт продажи;
- адресат сообщения;
- разрешение на production;
- команда удалить данные;
- команда повторить неизвестную внешнюю отправку.

Они определяются доверенной конфигурацией, сохранённым состоянием и отдельными разрешёнными операциями.

## Обязательные проверяемые сценарии DOC-11

Будущая реализация должна подтвердить как минимум:

1. Два одинаковых webhook одного события получают один call_ref; второй приём классифицируется как дубль и не запускает второй анализ.
2. Новое позднее событие того же звонка связывается с существующим call_ref, но не теряется как «дубль».
3. Одинаковый внешний call ID двух компаний не смешивается.
4. Payload пытается сменить company/schema — запрос отклоняется или остаётся в серверно заданном контуре.
5. Контрольная точка не сохранилась — внешний затратный шаг не запускается.
6. Транскрибация возвращает ответ не к тому operation_id/attempt — результат не повышается до подтверждённого.
7. Повтор транскрибации с тем же operation_id после сохранённого успеха не создаёт вторую равнозначную транскрипцию.
8. Privacy-gate blocked — вызов внешней LLM отсутствует.
9. LLM-пакет не содержит аудио, исходную транскрипцию, таблицу соответствия и Credentials.
10. LLM возвращает неизвестный код критерия/сломанный формат — результат не считается готовым анализом.
11. LLM пытается указать другую schema/компанию/адресата — это не влияет на систему.
12. LLM ссылается на несуществующий сегмент/knowledge chunk — ссылка не принимается как доказательство.
13. Ответ LLM сохранён только после структурной/privacy-проверки CORE.
14. Потерян ответ Supabase после записи — повтор сначала сверяет существующий результат и не создаёт дубль.
15. Dashboard A подставляет ID B — B не раскрывается.
16. Предполагаемый результат LLM и подтверждённый CRM факт остаются отдельными сущностями.
17. Исходящее действие сохраняется до обращения во внешний канал.
18. Повторное событие после созданного исходящего действия не создаёт второе эквивалентное действие.
19. Канал подтвердил доставку — повторная отправка той же операции запрещена.
20. Канал вернул таймаут после возможного приёма запроса — состояние становится неизвестным, слепой повтор не выполняется.
21. Канал точно отклонил запрос до внешнего эффекта и адаптер классифицировал ошибку как безопасно повторяемую — контролируемый повтор возможен.
22. Ошибка Credential классифицируется как требующая исправления, а не бесконечного retry.
23. Неизвестная версия контракта не исполняется «по догадке».
24. Логи ошибки содержат ID/коды/стадию, но не секреты и полный исходный текст разговора.

## Что остаётся после DOC-11

DOC-11 фиксирует смысл обмена, но не выбирает:

- точный JSON каждого API;
- HTTP routes и методы;
- n8n-ноды и количество workflow;
- SQL/таблицы/колонки;
- очередь и протокол блокировок;
- точные timeout/retry числа;
- финальные модели транскрибации/LLM;
- полный алгоритм версионирования;
- физическую модель доказательств.

DOC-12 должен связать эти контракты с логическими сущностями Supabase. DOC-13 затем закрепит правила версий, а DOC-14 — доказательства.

## Критерий DOC-11

Документ готов, если для каждой основной границы понятно:

- что идентифицирует звонок, операцию и попытку;
- какие версии входов обязаны сопровождать результат;
- что считается принятым, дублем и отклонённым запросом;
- какие состояния операции различаются;
- когда можно безопасно повторить действие;
- что сохраняется до следующего внешнего шага;
- как подтверждается транскрибация, анализ, CRM-факт и доставка;
- почему неизвестный внешний результат не превращается в слепой повтор;
- какие данные нельзя доверять внешнему payload/LLM.

SQL, n8n, Supabase, сервер и production в DOC-11 не изменялись.
