# Архитектура продукта

Базовое размещение — один российский сервер со связкой n8n, Supabase/PostgreSQL/pgvector, локального WhisperX для транскрибации/диаризации и отдельной серверной части дашборда. Исходное аудио и неанонимизированная транскрипция не покидают российский контур. Внешние LLM и embedding API получают только разрешённые подготовленные данные и остаются заменяемыми адаптерами. Подробности и обязательные проверки: [INFRASTRUCTURE_RU_SERVER](INFRASTRUCTURE_RU_SERVER.md).

Статус: архитектура верхнего уровня; Supabase-контур DB-01—DB-07 уже фактически создан и проверен. Следующий этап — n8n workflows. Отдельный backend/CORE-сервис для обработки звонков не создаётся.

## Настройки компании

В одном понятном месте должны находиться параметры, которые обычно меняются при внедрении:

- источник разговоров;
- правила фильтрации;
- параметры компании;
- промт анализа;
- критерии оценки;
- подключённые выходные каналы.

Настройки не должны быть разбросаны по workflow.

## Адаптеры

Адаптеры связывают продукт с внешними системами: Bitrix24, CRM, кабинетами операторов, Telegram, MAX и другими системами.

Добавление нового адаптера не должно требовать переписывания общей логики n8n-шаблона.

## CORE как логика внутри n8n

Термин **CORE** в проектной документации означает общие правила обработки, а **не отдельный сервис, backend или отдельный программный модуль**.

Физическая реализация CORE выполняется внутри n8n:

- Code-ноды — проверки контрактов, версий, scope, дублей, состояний, privacy/evidence gates и преобразования данных;
- обычные n8n-ноды — запросы к Supabase, WhisperX, LLM, CRM и каналам доставки;
- состояние и история сохраняются в Supabase, а не в памяти workflow.

Отдельный сервис CORE, отдельный API CORE и отдельный репозиторный код для обработки звонков не создаются.

Настройки конкретной компании не должны быть зашиты в Code-ноды: они берутся из доверенной конфигурации/Supabase/Credentials.

Общая логика workflow не должна зависеть от конкретного оператора, CRM или канала доставки.

## Нормативный порядок обработки

Для звонка, принятого к обработке:

получение события  
→ надёжная регистрация звонка  
→ защита от дубля  
→ получение аудио  
→ временное хранение  
→ транскрибация  
→ диаризация  
→ определение ролей МЕНЕДЖЕР/КЛИЕНТ  
→ анонимизация  
→ анализ  
→ сохранение версии результата и доказательств  
→ создание исходящего действия  
→ отправка обратной связи  
→ подтверждение доставки  
→ дашборд.

Фильтрация остаётся обязательной частью входного слоя. После надёжной регистрации и защиты от дубля правила компании могут завершить обработку ненужного звонка до получения аудио или другого дорогого этапа. Если решение о типе разговора возможно только по содержанию, дополнительная классификация допускается после транскрибации, как уже определено в INPUT_AND_FILTERING. Состояния, повторные и пропущенные звонки, результаты и доставка определены в [CALL_LIFECYCLE](specs/CALL_LIFECYCLE.md).

## Общая база знаний компании

У одной компании должен быть **единый актуальный источник знаний**, которым могут пользоваться бот первичного обращения, анализ звонков и будущие продукты.

При этом workflow продуктов независимы: анализ звонков не зависит от workflow бота и наоборот.

Каждый продукт должен получать только разрешённые опубликованные знания своей компании через отдельные ограниченные права.

Результат анализа должен сохранять версию знаний, на которой сделан вывод. Точный механизм версий, прав и публикации будет определён отдельными документационными задачами.

## Принцип внедрения

Новая компания должна подключаться преимущественно через настройки, адаптеры, собственные подключения, критерии оценки, промт и разрешённую базу знаний.

Общий шаблон n8n workflow и его Code-ноды при обычном внедрении не переписываются; меняются настройки, Credentials и адаптерные параметры.


## Инструменты как единый продукт

n8n содержит всю прикладную логику обработки звонка и управляет интеграциями: получает данные источников, выполняет проверки в Code-нодах, вызывает WhisperX/LLM и записывает факты и результаты этапов в Supabase, но не является долговременным хранилищем. Supabase хранит подтверждённое состояние, историю и версии и является источником истины для дашборда. WhisperX и LLM выполняют ограниченные вычислительные задачи; их ответы проверяются логикой Code-нод n8n до сохранения. Дашборд читает согласованные данные Supabase через отдельную серверную часть компании и не обращается к памяти выполнения n8n. Выходные адаптеры доставляют обратную связь и возвращают доступное подтверждение.

Полная карта ответственности, источников истины и переходов: [SYSTEM_INTERACTIONS](specs/SYSTEM_INTERACTIONS.md). Данные и показатели интерфейса: [DASHBOARD_DATA_MAP](DASHBOARD_DATA_MAP.md). Форматы payload, ноды, окончательные таблицы и SQL в эту задачу не входят.
