# Архитектура продукта

Базовое размещение — один российский сервер с отдельными сервисами n8n, Supabase/PostgreSQL/pgvector, локальной транскрибации, диаризации, псевдонимизации и серверных частей дашбордов. Исходное аудио и неанонимизированная транскрипция не покидают российский контур. Внешние LLM и embedding API получают только разрешённые подготовленные данные и остаются заменяемыми адаптерами. Подробности и обязательные проверки: [INFRASTRUCTURE_RU_SERVER](INFRASTRUCTURE_RU_SERVER.md).

Статус: архитектура верхнего уровня; детальные логические требования закреплены в профильных спецификациях. Физическая реализация SQL, workflow, программного кода и сервера ещё не начиналась.

## Настройки компании

В одном понятном месте должны находиться параметры, которые обычно меняются при внедрении:

- источник разговоров;
- правила фильтрации;
- параметры компании;
- промт анализа;
- критерии оценки;
- подключённые выходные каналы.

Настройки не должны быть разбросаны по workflow.

## Адаптеры

Адаптеры связывают продукт с внешними системами: Bitrix24, CRM, кабинетами операторов, Telegram, MAX и другими системами.

Добавление нового адаптера не должно требовать изменения CORE.

## CORE

CORE выполняет общую обработку и анализ.

Настройки конкретной компании не должны жить внутри CORE.

CORE не должно зависеть от того, откуда пришёл разговор, какой оператор или CRM используется и куда отправляется обратная связь.

## Нормативный порядок обработки

Для звонка, принятого к обработке:

получение события  
→ надёжная регистрация звонка  
→ защита от дубля  
→ получение аудио  
→ временное хранение  
→ транскрибация  
→ диаризация  
→ определение ролей МЕНЕДЖЕР/КЛИЕНТ  
→ анонимизация  
→ анализ  
→ сохранение версии результата и доказательств  
→ создание исходящего действия  
→ отправка обратной связи  
→ подтверждение доставки  
→ дашборд.

Фильтрация остаётся обязательной частью входного слоя. После надёжной регистрации и защиты от дубля правила компании могут завершить обработку ненужного звонка до получения аудио или другого дорогого этапа. Если решение о типе разговора возможно только по содержанию, дополнительная классификация допускается после транскрибации, как уже определено в INPUT_AND_FILTERING. Состояния, повторные и пропущенные звонки, результаты и доставка определены в [CALL_LIFECYCLE](specs/CALL_LIFECYCLE.md).

## Общая база знаний компании

У одной компании должен быть **единый актуальный источник знаний**, которым могут пользоваться бот первичного обращения, анализ звонков и будущие продукты.

При этом workflow продуктов независимы: анализ звонков не зависит от workflow бота и наоборот.

Каждый продукт должен получать только разрешённые опубликованные знания своей компании через отдельные ограниченные права.

Результат анализа должен сохранять версию знаний, на которой сделан вывод. Точный механизм версий, прав и публикации будет определён отдельными документационными задачами.

## Принцип внедрения

Новая компания должна подключаться преимущественно через настройки, адаптеры, собственные подключения, критерии оценки, промт и разрешённую базу знаний.

CORE при обычном внедрении не переписывается.


## Инструменты как единый продукт

n8n управляет процессом и интеграциями, получает данные источников и записывает факты и результаты этапов в Supabase, но не является долговременным хранилищем. Supabase хранит подтверждённое состояние, историю и версии и является источником истины для дашборда. Транскрибация/диаризация и LLM выполняют ограниченные вычислительные задачи; их ответы проверяет CORE. Дашборд читает согласованные данные Supabase через отдельную серверную часть компании и не обращается к памяти выполнения n8n. Выходные адаптеры доставляют обратную связь и возвращают доступное подтверждение.

Полная карта ответственности, источников истины и переходов: [SYSTEM_INTERACTIONS](specs/SYSTEM_INTERACTIONS.md). Данные и показатели интерфейса: [DASHBOARD_DATA_MAP](DASHBOARD_DATA_MAP.md). Форматы payload, ноды, окончательные таблицы и SQL в эту задачу не входят.
