# Текущее состояние проекта

Обновлено: 2026-09-25. Техническое проектирование требований.

## Режим

**Разрешено техническое проектирование в документации по одному ID.**

SQL, JSON workflow, программный код, n8n, Supabase, сервер и production пока не изменяются. Демонстрационный дашборд использует вымышленные данные и не подключён к Supabase.

## Последняя завершённая задача

**DOC-10 — описана изоляция компаний в одном серверном Supabase.**

Создан [ACCESS_AND_ISOLATION](specs/ACCESS_AND_ISOLATION.md).

Зафиксировано:

- единица изоляции — конкретная пара «компания + среда»;
- у каждой компании и среды отдельная schema одинаковой логической структуры;
- каждая обычная runtime-идентичность привязана только к одному контуру и минимальному набору операций;
- граница должна обеспечиваться доступом БД, а не только фильтром n8n/приложения;
- company/schema/tenant из payload, LLM или браузера не может переключить контур;
- общий postgres, service_role и административные ключи не используются обычными workflow/CORE/дашбордом;
- определены логические роли n8n, CORE, privacy-сервиса, чтения/публикации знаний, дашборда, мониторинга и администрирования без SQL/grants;
- test и production имеют отдельные schema, Credentials и настройки и не читают друг друга;
- внешняя LLM/embedding API и браузер не получают Credentials БД;
- для будущей реализации обязательны 24 отрицательных сценария чтения, записи, знаний, dashboard API, test/prod, подмены контекста и повторного использования соединений.

Точные PostgreSQL roles, grants/RLS, таблицы и пользовательская модель авторизации ещё не проектировались.

Цель: создать docs/specs/INTEGRATION_CONTRACTS.md и определить логические контракты источник → n8n → транскрибация → LLM → Supabase → выходной канал: обязательные идентификаторы, версии, статусы, подтверждения результата и поведение при ошибках без выбора конкретных n8n-нод или SQL.

До закрытия DOC-11 точные payload и интерфейсы между компонентами не считаются согласованными.
